[1. 현재 단계 목표]

게임 기획서(docs/GAME_CONCEPT.md)가 확정됐다. 게임 이름은 "여백 (Yeobaek)".

그런데 지금까지의 설계(2~4단계)는 "주사위를 굴리는 도시 미스터리 TRPG"를 가정하고 있었다.
능력치 6개, 직업, 주사위 판정, HP·돈·소지품, 운영자가 미리 쓴 시나리오, 게임 오버...
기획서는 이것들을 거의 전부 부정한다.

  - 판타지·오컬트 전면 배제, 평범한 하루의 날것 그대로의 감정에 집중
  - 복잡한 능력치 대신 온보딩 4요소 (대상·감정·상황·장르의 결)
  - 고정 시나리오 없이 LLM이 매번 새 단편 소설을 씀
  - 선택지는 "어디로 갈까"가 아니라 "어떤 태도로 받아낼까" (참아내기·피하기·받아치기...)
  - GAME OVER 없음. 플레이어가 스스로 마침표 → 에필로그
  - 완성된 이야기는 "여백의 서재"에 쌓임

이번 단계 목표:
  - "무엇을 만드는가"를 적은 문서(02 룰북, 03 DB, 04 API, 05 에이전트)를 새 기획 기준으로 다시 쓴다
  - "어떻게 만드는가"(로그인, SSE, 턴 잠금, 타입 자동 생성, git 규칙)는 최대한 그대로 살린다
  - 화면 톤("소설책을 읽는 경험")을 프론트가 따를 수 있는 규칙 문서로 만든다 (09번 신설)
  - 아직 정하지 않은 값은 "가정값"으로 표시해 나중에 바꾸기 쉽게 한다 (08번)

사용자와 먼저 정한 것 (질문으로 확정):
  - 게임 수치: 전부 제거, 감정 상태만 추적
  - 온보딩: 예시 칩 선택 + 직접 입력
  - 결말: 사용자 주도 (기획서 최종본 5장)


[2. 사용한 기술/핵심 개념 (비유 설명 포함)]

(1) "무엇"과 "어떻게"를 분리해 둔 설계의 힘
    = 집의 인테리어를 통째로 바꿔도 전기 배선은 그대로 쓰는 것.
    기획이 180도 바뀌었는데도 로그인, DB 접속 방식, SSE 스트리밍, 턴 잠금, 중복 요청 방지,
    에러 형식, 타입 자동 생성은 거의 손대지 않았다.
    2~4단계에서 "게임 규칙"과 "기술 뼈대"를 서로 다른 문서로 나눠둔 덕분이다.
    바뀐 건 주로 02(룰북)·03(표 구조)·04(주고받는 모양)·05(AI 역할)였다.

(2) emotion vs mood — 이름을 둘로 나눈 이유
    = 여행 출발지와 현재 위치.
    emotion은 온보딩에서 고른 "출발 감정"(바뀌지 않음),
    mood는 이야기가 흘러가며 "지금 느끼는 감정"(턴마다 바뀜)이다.
    하나의 이름으로 두 가지를 부르면 코드에서 반드시 헷갈린다. 용어 사전에 못 박았다.

(3) 감정 상태를 숫자 두 개로 표현
    = 날씨를 "맑음/흐림"(방향)과 "바람 세기"(세기)로 나누는 것.
    valence(-2~+2, 괴로움↔편안함)와 intensity(1~5, 세기).
    이 두 숫자를 턴마다 저장하면 이어서 "감정의 파동" 선이 된다.
    AI는 새 감정을 "제안"만 하고, 파이썬이 "한 턴에 ±2까지만"으로 잘라 저장한다.
    (예전 원칙 "주사위는 AI가 굴리지 않는다"가 "숫자는 AI가 확정하지 않는다"로 바뀐 것)

(4) 태도 코드 (attitude)
    = 선택지에 붙은 이름표.
    선택지 문장은 AI가 매번 자유롭게 쓰지만, 각 선택지에 "참아내기/피하기/받아치기/털어놓기/흘려보내기"
    중 하나의 이름표를 붙이게 했다.
    이름표가 있으면 ① 한 번에 나온 선택지들이 같은 태도로 겹치는지 검사할 수 있고,
    ② 에필로그와 서재에서 "오늘 나는 세 번 참았다" 같은 통계를 보여줄 수 있다.

(5) SSE 이벤트를 7개에서 4개로 줄임
    = 택배를 여러 상자로 나눠 보내다가, 마지막에 "전체 명세서"를 한 장 넣는 방식.
    turn_started → narration_delta(여러 번) → turn_completed → (실패 시 error)
    선택지·감정·장면 메모는 전부 마지막 turn_completed 한 상자에 담았다.
    이벤트 종류가 적을수록 "중간에 하나를 놓쳤을 때" 생길 수 있는 경우의 수가 줄어든다.
    게다가 프롤로그·행동·에필로그 세 가지 요청이 전부 같은 4개 이벤트를 쓰므로,
    프론트는 스트림 처리 함수를 하나만 만들면 된다.

(6) "거절하지 않고 현실로 번역하기"
    = 아이가 "나는 공룡이야!"라고 하면 "공룡을 좋아하는 아이구나" 하고 받아주는 것.
    온보딩에 "마법사"라고 써도 막지 않고 "마술 동호회에 빠진 회사원"처럼 현실 인물로 해석한다.
    판타지 배제 원칙은 지키면서도, 유저를 튕겨내지 않는 게 이 게임의 톤이다.

(7) 감정을 다루는 게임의 안전장치
    기획서가 무기력·슬픔 같은 감정을 정면으로 다루기 때문에,
    "어두운 감정을 그리는 것"과 "위험한 방향으로 흐르는 것"을 구분하는 규칙을 넣었다.
    자해·자살의 방법이나 미화는 쓰지 않고, 실제 위기 신호가 보이면 이야기는 주인공을 다정하게 붙잡고
    화면에는 자살예방상담전화 109를 조용히 안내한다. 배포 전에 반드시 완성하도록 로드맵에 못 박았다.

[핵심 설계 스니펫 - AI의 감정 제안을 파이썬이 검증]

    def clamp_mood(prev: Mood, proposed: Mood) -> Mood:
        """
        기록원 AI가 제안한 새 감정을 규칙 안으로 잘라낸다.
        - valence는 -2~+2, intensity는 1~5
        - 한 턴에 움직일 수 있는 폭은 ±2까지 (감정의 널뛰기 방지)
        """
        valence = clamp(proposed.valence, prev.valence - 2, prev.valence + 2)
        valence = clamp(valence, -2, 2)
        intensity = clamp(proposed.intensity, prev.intensity - 2, prev.intensity + 2)
        intensity = clamp(intensity, 1, 5)
        ...

[핵심 설계 스니펫 - 이야기 쓰기 요청 3종이 공유하는 SSE 흐름]

    turn_started      -> {"turn_id","turn_number","turn_type"}
    narration_delta   -> {"text": "..."}   (여러 번, 그대로 이어붙이면 전체 서술)
    turn_completed    -> {"turn": 저장된 턴 전체, "session": 이야기 상태}
    error             -> {"code","message"}  (이 턴은 저장되지 않음)

[5. 오늘의 학습 포인트]

포인트 1. 기획이 바뀌어도 살아남는 설계가 좋은 설계다.
  이번에 기획이 통째로 바뀌었지만 기술 뼈대는 거의 그대로 남았다.
  "무엇을 만드는가(규칙)"와 "어떻게 만드는가(기술)"를 다른 문서, 다른 층으로 나눠둔 덕분이다.

포인트 2. 게임의 "수치"는 줄일수록 이야기가 산다. 대신 남은 수치는 엄격하게.
  숫자로 관리하는 건 감정(valence, intensity) 두 개뿐이다.
  그 두 개만큼은 범위와 한 턴 변화량을 파이썬이 철저히 지킨다.
  수치가 적을수록 규칙이 흔들리면 게임 전체가 흔들리기 때문이다.

포인트 3. 감정을 다루는 서비스는 안전장치가 기능이다.
  이 게임은 무기력·슬픔을 정면으로 다룬다. 그래서 안전 규칙을 "나중에 붙일 옵션"이 아니라
  룰북·에이전트·화면·로드맵 전부에 처음부터 넣고, 배포 전 필수 단계로 못 박았다.
