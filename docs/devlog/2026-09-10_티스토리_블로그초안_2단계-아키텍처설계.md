### 🗺️ 1. 전체 그림부터 그렸다

먼저 데이터가 어디서 출발해 어디로 가는지를 그렸다.

```
브라우저(Next.js)
   ├─ 로그인 ──────────────> Supabase Auth  (신분증 발급소)
   └─ 게임 플레이 요청 ────> FastAPI        (게임 마스터의 책상)
                                  ├─ LangGraph ──> LLM API
                                  └─ Supabase PostgreSQL + pgvector
```

각 부품의 역할을 비유로 정리하면 이렇다.

* **Next.js** — 게임기 화면과 컨트롤러
* **Supabase Auth** — 신분증 발급소 ("이 사람 회원 맞음" 도장)
* **FastAPI** — 게임 마스터의 책상. **모든 판단이 여기서 일어난다**
* **LangGraph** — 여러 명의 보조 진행자 팀
* **PostgreSQL** — 게임 기록장
* **pgvector** — GM의 기억 서랍

그림을 그리고 나니 자연스럽게 "그럼 이 경계에서 무슨 형식으로 주고받지?"라는 질문이 나왔다.

그게 다음 문서로 이어졌다.

### 🎲 2. AI에게 주사위를 굴리게 하면 안 된다

설계하면서 가장 먼저 못 박은 원칙이다.

TRPG는 주사위 게임이다. 그래서 처음엔 이렇게 만들면 되겠다고 생각했다.

```
"AI야, 이 플레이어가 경비원을 설득하려고 해.
 주사위 굴려서 성공인지 실패인지 판단하고 서술해줘."
```

그런데 이건 치명적인 실수다.

**AI는 난수 생성기가 아니라 "그럴듯한 말을 만드는 기계"다.**

주사위를 굴리라고 하면 진짜 무작위를 만드는 게 아니라, 이야기 흐름상 그럴듯한 숫자를 **고른다**.

* 극적인 장면에서는 계속 20이 나온다
* 플레이어가 불쌍해 보이면 성공시켜준다
* 같은 상황을 두 번 시켜도 결과가 비슷하게 나온다

그래서 이렇게 나눴다.

```python
def roll_dice(stat_value: int, difficulty: str) -> DiceCheck:
    """
    주사위를 굴리고 성패를 판정한다.
    AI를 쓰지 않는 이유: AI는 진짜 무작위를 만들지 못하고,
    극적이거나 유저에게 유리한 숫자를 '고르는' 경향이 있다.
    """
    dice = random.randint(1, 20)          # 순수 주사위값
    modifier = stat_value * 2             # 능력치 보정
    total = dice + modifier
    dc = DIFFICULTY_TABLE[difficulty]     # easy=10 normal=14 hard=18 extreme=22

    if dice == 20:    outcome = "critical_success"
    elif dice == 1:   outcome = "critical_failure"
    elif total >= dc: outcome = "success"
    else:             outcome = "failure"
```

파이썬이 주사위를 굴려 결과를 확정한 다음, AI에게는 이렇게 넘긴다.

> 💡 "17이 나왔고 성공이야. 이 장면을 소설처럼 묘사해줘."

**판정은 코드, 묘사는 AI.** 이 경계를 절대 넘지 않기로 했다.

같은 원칙을 상태 변화에도 적용했다.

AI는 "HP를 20 깎겠습니다"라고 **제안**만 할 수 있고, 실제로 깎는 건 파이썬이다.

```python
def apply_state_changes(session, archivist_output):
    """
    AI의 '제안'을 실제 상태에 반영한다.
    AI가 '당신은 갑자기 100억을 얻었습니다'라고 해도
    파이썬이 상한선에서 잘라낸다.
    """
    hp_delta = clamp(archivist_output.resource_delta.hp, -40, 30)   # 한 턴 변화 상한
    new_hp = clamp(session.resources.hp + hp_delta, 0, session.resources.max_hp)
```

### 📄 3. 프론트와 백엔드 사이에 "계약서"를 썼다

이번 설계에서 가장 공을 들인 문서다.

프론트엔드가 `character.hp`를 기대하는데 백엔드가 `character.health`를 보내면 화면이 빈다.

이건 실력 문제가 아니라 **구조 문제**다. 사람의 주의력으로 막으려 하면 반드시 실패한다.

그래서 두 가지를 했다.

**첫째, 계약서 문서를 만들었다.**

주고받을 모든 API의 주소·요청 형식·응답 형식을 문서 하나에 전부 적었다.

그리고 규칙을 하나 정했다.

> 💡 계약서에 없는 API는 존재하지 않는 것으로 간주한다. 필요하면 문서에 먼저 추가하고 코드를 짠다.

**둘째, 타입을 자동으로 생성하게 만들었다.**

```
백엔드 Pydantic 모델
   ↓ FastAPI가 자동으로 만들어주는 /openapi.json
   ↓ npx openapi-typescript
프론트엔드 src/types/api.ts  (자동 생성, 손으로 고치지 않음)
```

이렇게 하면 백엔드에서 필드 이름을 바꾸는 순간, 프론트엔드에서 **컴파일 에러**가 난다.

"에러가 나는 게 성공"이라는 게 처음엔 이상하게 들렸다.

하지만 어긋남이 **배포 전에** 잡힌다는 뜻이다. 이 장치가 없으면 그 어긋남을 결국 유저가 발견한다.

### 📡 4. 왜 WebSocket이 아니라 SSE인가

AI가 이야기를 만드는 데는 10초쯤 걸린다.

그동안 빈 화면을 보여주면 유저는 떠난다. 그래서 글자가 만들어지는 대로 흘려보내는 방식이 필요했다.

후보는 두 가지였다.

* **SSE** — 라디오 방송. 방송국(서버)이 계속 말하고 청취자(브라우저)는 듣기만 한다
* **WebSocket** — 전화 통화. 양쪽이 동시에 말할 수 있지만 그만큼 관리가 복잡하다

TRPG는 "내가 행동을 말하고 → GM이 길게 답한다"의 반복이다.

서버가 일방적으로 쏟아내는 구조라 한 방향이면 충분했다. 그래서 **SSE**를 골랐다.

그리고 서버가 보낼 이벤트 종류를 미리 다 정해뒀다.

* `turn_started` — 턴이 시작됐다
* `dice_roll` — 주사위 결과 (프론트는 이때 굴리는 연출을 보여준다)
* `narration_delta` — 서술 조각. 여러 번 오고, 그대로 이어붙이면 전체 문장
* `state_patch` — 상태 변화량 (`mental: -3` 처럼 델타값)
* `turn_completed` — 턴 종료 + **최종 전체 상태**
* `error` — 실패

여기서 안전장치를 하나 넣었다.

마지막 `turn_completed`에는 변화량이 아니라 **최종 전체 상태**를 담는다.

프론트엔드는 중간 이벤트로 부드러운 애니메이션을 주되, 최종 화면 값은 반드시 이걸로 덮어쓴다.

> 💡 네트워크가 불안해서 중간 이벤트를 하나 놓쳐도, 화면이 DB와 어긋나지 않게 하기 위해서다.

### 🔒 5. 전송 버튼 연타를 막는 두 겹의 장치

유저는 응답이 느리면 전송 버튼을 연타한다.

그러면 턴이 여러 개 동시에 처리되면서 HP가 두 번 깎이는 사고가 난다.

두 겹으로 막기로 했다.

**첫 번째, 턴 잠금.**

게임 세션에 `processing` 상태를 뒀다. 화장실 문의 "사용중" 표시와 같다.

```
행동 요청 도착
  → status를 'active' → 'processing' 으로 조건부 UPDATE
  → 못 바꿨다? = 이미 처리 중 = HTTP 409 반환
  → 처리가 끝나면 다시 'active'
```

**두 번째, 멱등성.**

프론트가 요청마다 고유 번호(`client_action_id`)를 붙인다.

백엔드는 이미 본 번호면 새 턴을 만들지 않고 기존 결과를 그대로 돌려준다.

인터넷이 끊겼다 다시 연결되면서 같은 요청이 두 번 가더라도 턴은 하나만 생긴다.

> 🔍 가장 위험한 버그는 **오류가 났는데 잠금이 안 풀리는 것**이다. 그 세션은 영원히 잠긴다. 그래서 `try / finally`로 반드시 풀고, 5분 넘게 processing이면 자동 해제하도록 설계에 못 박았다.

### 🧩 6. AI 한 명이 아니라 팀으로 나눴다

처음엔 이런 프롬프트를 생각했다.

```
"유저가 이런 행동을 했어. 판정이 필요한지 정하고, 주사위 결과를 반영해서,
 재밌게 서술하고, HP 변화를 계산하고, 요약도 남기고, JSON으로 출력해줘."
```

이러면 이런 일이 벌어진다.

* 서술이 좋아지면 JSON 형식이 깨진다
* 형식을 잘 지키면 서술이 딱딱해진다
* 하나만 고치려 해도 프롬프트 전체가 흔들린다

한 사람에게 요리와 서빙과 계산을 동시에 시키는 것과 같다.

그래서 LangGraph로 역할을 나눴다.

| 노드 | 담당 | AI 사용 |
|---|---|---|
| 판정관 | 판정이 필요한가? 어떤 능력치로? | O (객관식) |
| 주사위 | 실제 굴림과 성패 계산 | X (파이썬) |
| 기억 검색 | 관련된 과거 장면 회수 | X (pgvector) |
| 이야기꾼 | 서술 생성 | O (스트리밍) |
| 기록원 | 상태 변화 추출, 요약 | O (객관식) |
| 검증/반영 | 상한 적용, DB 저장 | X (파이썬) |

여기서 판정관과 기록원은 **구조화 출력(Structured Output)**을 쓴다.

AI에게 "자유롭게 답해"가 아니라 **"이 빈칸을 채워"**라고 시키는 방식이다.

```python
class RefereeDecision(BaseModel):
    needs_check: bool                    # 판정이 필요한가
    stat: Literal["strength","agility","intellect",
                  "perception","charm","will"] | None
    difficulty: Literal["easy","normal","hard","extreme"] | None
    reason: str                          # 왜 그렇게 정했는지 (디버깅용)
```

객관식으로 물어보니 AI가 엉뚱한 형식으로 답할 수가 없다.

JSON 파싱 실패나 키 이름 오타 같은 사고가 사라진다.

한 가지 더 정한 것이 있다. **이걸 한 번에 다 만들지 않는다.**

* Step 6 — 이야기꾼 노드 하나만
* Step 7 — 스트리밍 붙이기
* Step 8 — 판정관 + 주사위 + 기록원
* Step 9 — 기억 검색

6개를 동시에 만들면 어디서 틀렸는지 절대 못 찾는다.

### 🗓️ 7. 순서를 Step 0부터 12까지 못 박았다

마지막으로 무엇부터 할지를 정했다.

```
[기반 공사]   Step 1  DB 스키마
              Step 2  로그인/인증
              Step 3  타입 자동생성 + 목(mock) API
[게임 준비]   Step 4  캐릭터 생성
              Step 5  시나리오 선택 + 세션 시작   ← AI 없이도 게임 껍데기 완성
[AI 투입]     Step 6  GM 한 명 (동기 응답)
              Step 7  스트리밍
              Step 8  주사위 + 상태 관리
              Step 9  장기 기억                  ← MVP 완성
[마무리]      Step 10 NPC / Step 11 배포 / Step 12 다듬기
```

원칙은 세 가지로 정했다.

* 한 Step이 끝나면 반드시 커밋한다 (되돌아갈 지점 만들기)
* 한 Step이 끝나면 개발 로그와 블로그 초안을 쓴다
* **"동작 확인 방법"을 통과하지 못하면 다음 Step으로 넘어가지 않는다**

각 Step마다 "여기서 막힐 것 같다"는 지점도 미리 적어뒀다.

* **Step 2** — JWT 검증은 비전공자에게 가장 어려운 구간이라 하루를 더 잡아뒀다
* **Step 7** — SSE 청크가 한글 글자 중간에서 잘려 깨진다. `TextDecoder({stream:true})`가 필수라고 메모해뒀다
* **Step 11** — Render 무료 티어는 15분 쉬면 서버가 잠든다. 깨우는 로딩 화면을 미리 계획에 넣었다

### ✅ 정리하며

코드를 한 줄도 안 짠 날이었지만, 지금까지 중에 가장 밀도가 높았다.

특히 **"AI에게 시킬 일과 시키면 안 되는 일을 나누는 것"**이 AI 서비스 설계의 절반이라는 걸 알게 됐다.

AI를 만능으로 쓰려고 하면 통제할 수 없는 시스템이 된다.

역할을 좁게 자를수록 오히려 결과가 안정된다.

다음 편은 Step 1 — Supabase에 실제 테이블을 만든다. 캐릭터·세션·턴 기록·장기 기억까지 7개 테이블과, 남의 데이터가 보이지 않게 막는 RLS 정책을 SQL로 작성할 예정이다.

### 💡 오늘의 핵심 3줄 요약

* **주사위와 계산은 AI에게 맡기지 않는다.** AI는 난수 생성기가 아니다. 판정은 파이썬이 하고 AI는 묘사만 한다.
* **프론트와 백엔드의 타입은 사람이 맞추면 반드시 어긋난다.** 자동 생성 파이프라인을 만들면 어긋나는 순간 컴파일 에러가 난다.
* **실패했을 때의 동작을 성공 코드보다 먼저 설계한다.** 특히 세션 잠금은 `finally`로 반드시 풀어야 유저가 먹통을 안 만난다.
