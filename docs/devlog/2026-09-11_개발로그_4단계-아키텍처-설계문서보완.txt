[1. 현재 단계 목표]

2단계에서 설계 문서 8종(docs/01~08)을 만들었다.
그런데 코드를 짜기 직전에 문서 전체를 다시 한 줄씩 대조해 보니,
"문서끼리 서로 다른 말을 하는 곳"과 "아무도 정하지 않은 빈칸"이 25군데 나왔다.

이대로 프론트/백엔드 세션에 넘기면 이런 일이 생긴다.
  - 두 세션이 각자 다른 문서를 믿고 짜서, 만나는 지점에서 안 맞는다
  - 빈칸은 각 세션이 "알아서" 채우는데, 둘이 다르게 채운다
  - 규칙 충돌(push 한다/안 한다)로 세션마다 행동이 달라진다

이번 단계 목표:
  - 문서 간 충돌을 하나로 통일한다 (CLAUDE.md를 기준으로)
  - API 계약서의 빈칸(인벤토리 변화, 실패한 턴, 중복 요청 등)을 채운다
  - "나중에 알면 코드를 뜯어야 하는 것"(DB 접속 방식, 테이블 칸 누락)을 지금 확정한다
  - 저장소에 숨어 있던 사고 요인을 찾아 Step 0.5(정리 작업)로 만든다

※ 사용자 방침: 이번에는 "문서만 수정", 실제 실행(파일 삭제, 코드 수정)은 하지 않는다.
  → 실행이 필요한 것은 전부 로드맵 Step 0.5와 작업 지시서에 할 일로 적어두었다.


[2. 사용한 기술/핵심 개념 (비유 설명 포함)]

(1) 트랜잭션 (Transaction)
    = 은행 이체.
    "내 통장에서 출금"과 "상대 통장에 입금"은 둘 다 되거나, 둘 다 안 되어야 한다.
    출금만 되고 입금이 안 되면 돈이 증발한다.
    게임에서는 "턴 기록 저장"과 "HP 깎기"가 이 관계다.
    그런데 설치돼 있던 supabase 파이썬 라이브러리(REST 방식)는 요청 하나에 작업 하나라서
    이 둘을 한 묶음으로 처리할 수 없었다.
    → 백엔드는 Postgres에 직접 연결(psycopg)하기로 확정했다.

(2) 커넥션 풀러 (Session pooler)
    = 건물 대표 전화번호.
    직원 개인 번호(Direct connection)는 새 방식(IPv6) 전화기로만 걸리는데,
    배포 서버(Render)나 일부 가정용 인터넷은 옛날 전화기(IPv4)밖에 없다.
    대표 번호(pooler)는 어느 전화기로도 걸린다.
    → 로컬과 배포 모두 pooler 주소 하나로 통일했다.

(3) 소프트 삭제 (Soft delete)
    = 도서관 책을 버리지 않고 "폐기" 도장만 찍는 것.
    캐릭터를 진짜 지우면, 그 캐릭터로 했던 지난 게임 기록이 "주인 없는 기록"이 되어 깨진다.
    그래서 deleted_at 칸에 날짜만 적고, 목록에서만 안 보이게 한다.

(4) DB 트리거
    = 자동문 센서.
    사람이 문 앞에 서면(회원가입) 누가 버튼을 안 눌러도 문이 열린다(프로필 생성).
    원래 설계는 "프론트가 /me를 먼저 불러야 프로필이 생긴다"는 숨은 순서가 있었는데,
    순서를 한 번만 어겨도 캐릭터 생성이 에러가 난다.
    트리거로 바꾸면 순서 자체가 사라진다.

(5) 멱등성(Idempotency) 상황표
    = 택배 송장번호.
    같은 송장번호로 두 번 접수되면 택배를 두 번 보내지 않는다.
    이번에 "같은 번호가 처리 중일 때 또 오면?", "처리하다 실패한 번호가 다시 오면?"처럼
    애매했던 경우를 표로 전부 정했다. (04번 문서 7-2)

(6) Heartbeat (연결 유지 신호)
    = 통화 중에 "여보세요? 듣고 있어요?" 하는 것.
    AI가 주사위 판정과 기억 검색을 하느라 첫 글자가 나오기 전 한참 조용하면,
    프론트는 "끊겼나?" 하고 30초 뒤 타임아웃을 낸다.
    그래서 서버가 15초마다 ": ping" 한 줄을 보내 "아직 살아있어"를 알린다.

(7) 404로 숨기기
    = 아파트 경비실에서 "그 호수엔 아무도 안 살아요".
    남의 세션에 접근하면 "권한 없음(403)"이 아니라 "없음(404)"으로 답한다.
    403이라고 하면 "그 번호의 세션이 있긴 하다"는 정보를 흘리게 되기 때문이다.

[핵심 설계 스니펫 - 턴 잠금을 SQL 한 줄로]

    update game_sessions
       set status = 'processing', locked_at = now()
     where id = %(session_id)s and user_id = %(user_id)s
       and (status = 'active'
            or (status = 'processing' and locked_at < now() - interval '5 minutes'))
    returning *;
    -- 돌아온 줄이 0개면 "누가 이미 처리 중" → 409

    * "확인하고 → 바꾸기"를 두 번에 나눠 하면, 그 사이에 다른 요청이 끼어들 수 있다.
      조건을 UPDATE 안에 넣으면 DB가 한 번에 처리해서 끼어들 틈이 없다.
    * 5분 조건은 서버가 처리 도중 죽었을 때 세션이 영원히 잠기는 걸 막는 마지막 안전장치.

[5. 오늘의 학습 포인트]

포인트 1. 설계 문서도 "코드 리뷰"가 필요하다.
  문서 8개를 각각 읽으면 다 그럴듯하다. 문제는 문서와 문서 사이에 있다.
  API 계약서는 시나리오 난이도를 준다고 하는데 DB 표에는 그 칸이 없었다.
  하나씩 볼 땐 안 보이고, 나란히 놓고 대조해야 보인다.

포인트 2. "지금 정하지 않아도 되게" 설계하는 것도 설계다.
  AI 모델은 아직 바꿔가며 실험할 예정이다. 그런데 임베딩 모델은 DB 칸 크기에 묶여 있다.
  그래서 기억 테이블을 만드는 시점 자체를 Step 9 직전으로 미뤘다.
  모델 이름도 코드에 박지 않고 환경변수로 받게 했다.
  "결정을 미룰 수 있는 구조"를 만들면, 결정을 못 한 채로도 앞으로 나아갈 수 있다.

포인트 3. 규칙은 한 곳에만 둔다.
  push 규칙이 4군데, 직업 보너스 표가 (잠재적으로) 프론트/백엔드 2군데에 있을 뻔했다.
  같은 규칙이 두 곳에 있으면 한쪽만 고치는 날이 반드시 온다.
  그래서 게임 규칙표는 백엔드가 API로 내려주고, 프론트는 받아서 그리기만 한다.
