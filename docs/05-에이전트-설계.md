# 05. AI 에이전트 설계 (LangGraph)

> 🎯 **한 명의 만능 AI에게 다 시키지 않고, 역할별로 나눕니다.**
> 💡 혼자 다 하는 GM보다, "규칙 담당 / 이야기 담당 / 기록 담당"이 나뉜 팀이 실수가 적습니다.
> 💡 그리고 어디서 잘못됐는지 **정확히 그 사람만 고치면** 됩니다.

---

## 1. 왜 멀티 에이전트인가?

AI에게 이런 프롬프트를 준다고 해봅시다.

```
"유저가 이런 행동을 했어. 판정이 필요한지 정하고, 주사위 결과를 반영해서,
 재밌게 서술하고, HP 변화를 계산하고, 요약도 남기고, NPC 대사도 만들어줘.
 아 그리고 JSON으로 출력해줘."
```

이러면 이런 일이 벌어집니다.
- 서술이 좋으면 JSON 형식이 깨짐
- JSON을 잘 지키면 서술이 딱딱해짐
- 하나만 고치려 해도 프롬프트 전체가 흔들림

> 💡 **한 사람에게 요리 + 서빙 + 계산을 동시에 시키면 다 엉망이 됩니다.**
> 나눠서 각자 하나만 잘하게 하는 게 멀티 에이전트입니다.

## 3. 각 노드 상세

### 노드 1. 판정관 (Referee) — AI

**입력**: 유저 행동, 캐릭터 능력치, 현재 상황
**출력** (반드시 이 구조로):
```python
class RefereeDecision(BaseModel):
    needs_check: bool                    # 판정이 필요한가
    stat: Literal["strength","agility","intellect",
                  "perception","charm","will"] | None
    skill_label: str | None              # "설득", "관찰" 등 화면 표시용
    difficulty: Literal["easy","normal","hard","extreme"] | None
    reason: str                          # 왜 그렇게 정했는지 (디버깅용)
```

> 💡 **구조화 출력(Structured Output)이란?**
> AI에게 "자유롭게 답해"가 아니라 **"이 빈칸을 채워"**라고 시키는 방식입니다.
> LangChain의 `with_structured_output(RefereeDecision)`을 쓰면
> AI 응답이 자동으로 이 Pydantic 객체로 변환됩니다.
> → JSON 파싱 실패, 키 이름 오타 같은 사고가 사라집니다.

**모델**: 빠르고 싼 모델 (판단만 하면 되므로)

> 💡 MVP에서는 판정관이 **"상황 보정치"를 정하지 않습니다.** (02번 문서 4장) 숫자는 전부 규칙표에서 나옵니다.

### 노드 2. 주사위 (Dice) — 파이썬

```python
def roll_dice(stat_value: int, difficulty: str) -> DiceCheck:
    """
    주사위를 굴리고 성패를 판정한다.
    stat_value는 기본 능력치가 아니라 직업 보너스까지 적용된 effective_stats 값이다.
    반환값 DiceCheck는 SSE dice_roll 이벤트, turns.dice_check 컬럼과 같은 모델이다 (04번 문서 7-5 ②).
    AI를 쓰지 않는 이유: AI는 진짜 무작위를 만들지 못하고,
    유저에게 유리하거나 극적인 숫자를 '고르는' 경향이 있다.
    """
    dice = random.randint(1, 20)
    modifier = stat_value * 2
    total = dice + modifier
    dc = DIFFICULTY_TABLE[difficulty]

    if dice == 20:  outcome = "critical_success"
    elif dice == 1: outcome = "critical_failure"
    elif total >= dc: outcome = "success"
    else: outcome = "failure"
    ...
```

### 노드 3. 기억 검색 (Recall) — pgvector

**입력**: 유저 행동 텍스트
**동작**:
1. 유저 행동을 임베딩(숫자 좌표)으로 변환
2. `memories` 테이블에서 **같은 세션 안에서** 코사인 유사도 상위 5개 조회
3. `importance`가 높은 것에 가중치

**출력**: 과거 장면 요약 문자열 목록

> 💡 **왜 필요한가?**
> 50턴쯤 진행되면 대화 기록이 너무 길어져서 AI에게 전부 줄 수 없습니다(비용/길이 제한).
> 그렇다고 최근 5턴만 주면 "20턴 전에 만난 그 사람"을 GM이 까먹습니다.
> → **최근 몇 턴 + 지금 상황과 관련된 과거 기억**만 골라서 줍니다.

### 노드 4. 이야기꾼 (Narrator) — AI (스트리밍)

**입력** (프롬프트에 들어가는 것 전부):
| 항목 | 출처 |
|---|---|
| 시나리오 톤 지시문 | `scenarios.gm_guideline` |
| 캐릭터 시트 | `characters` |
| 현재 자원/세계 상태 | `game_sessions` |
| 지금까지의 줄거리 요약 | `game_sessions.summary_so_far` |
| 최근 5턴 대화 | `turns` |
| 관련 장기 기억 | 노드 3 결과 |
| 유저 행동 | 이번 요청 |
| **주사위 판정 결과** | 노드 2 결과 |

**출력**: 자유 텍스트 (150~400자), **스트리밍**

**절대 규칙 (시스템 프롬프트에 명시)**:
- 2인칭("당신은...")으로 서술한다
- 유저 캐릭터의 **대사나 결정을 대신 만들지 않는다**
- 판정 결과를 **뒤집지 않는다** (실패인데 성공한 것처럼 쓰지 않기)
- 숫자(HP 등)를 직접 말하지 않는다 → "옆구리가 욱신거린다"처럼 묘사로
- 유저에게 "무엇을 하시겠습니까?"로 끝맺어 선택권을 넘긴다

**모델**: 문장력이 좋은 모델 (여기가 게임 품질의 90%)

### 노드 5. 기록원 (Archivist) — AI

**입력**: 이번 턴의 서술 + 이전 상태 + **현재 소지품 이름 목록**
(소지품을 없앨 때 목록에 있는 이름을 **정확히 그대로** 고르게 하기 위함. "휴대폰"을 "스마트폰"으로 쓰면 제거가 무시됨)

**출력**:
```python
class ArchivistOutput(BaseModel):
    resource_delta: ResourceDelta       # {"hp": -5, "mental": -3, "money": 0}
    inventory_add: list[Item]
    inventory_remove: list[str]
    world_state_update: WorldStateUpdate
    memory_content: str                 # 장기 기억에 저장할 한 문장
    memory_importance: int              # 1~5
    suggestions: list[str]              # 추천 행동 3개
```

**모델**: 빠르고 싼 모델

> ⚠️ **이 노드는 스트리밍하지 않습니다.**
> 이야기꾼의 서술이 다 나온 뒤에 실행되므로, 유저는 이미 글을 읽고 있습니다.
> 그 사이에 조용히 끝납니다. (체감 지연 없음)

### 노드 6. 검증/반영 (Apply) — 파이썬

```python
def apply_state_changes(session, archivist_output):
    """
    AI의 '제안'을 실제 상태에 반영한다.
    AI를 신뢰하지 않고 전부 검사하는 것이 핵심.
    """
    # 1) 한 턴 변화량 상한 적용 (02번 문서 3장)
    hp_delta = clamp(archivist_output.resource_delta.hp, -40, 30)

    # 2) 절대 범위 적용
    new_hp = clamp(session.resources.hp + hp_delta, 0, session.resources.max_hp)

    # 3) 인벤토리: 한 턴 3개 제한, 없는 아이템 제거 시도는 무시 (02번 문서 3장 소지품 규칙)
    # 4) flags: bool 또는 0~10 정수만 허용, 키는 snake_case만. 그 외 폐기 + 경고 로그
    # 5) 게임 오버 판정 (02번 문서 7장, 우선순위 defeat > victory > timeout)
    #    - hp == 0 또는 mental == 0            → ended_defeat
    #    - flags가 scenario.goal_flags를 모두 만족 → ended_victory
    #    - turn_count >= scenario.max_turns     → ended_timeout
    # 6) 실제로 반영된 값으로 StatePatch를 만든다 (SSE state_patch, turns.state_patch 공용)
    # 7) DB 저장: 한 트랜잭션으로 (03번 문서 6장)
    #    turns INSERT + game_sessions UPDATE(자원, 세계상태, turn_count+1, status, locked_at=null)
    #    → 게임 오버면 status를 'active'가 아니라 'ended_*'로 저장
```

## 4. 상태 객체 (LangGraph State)

그래프의 노드들이 돌려쓰는 "공용 메모지"입니다.

```python
class GameTurnState(TypedDict):
    # 입력 (변하지 않음)
    session_id: str
    player_input: str
    character: CharacterSheet
    resources: Resources
    world_state: WorldState
    recent_turns: list[TurnSummary]
    gm_guideline: str

    # 각 노드가 채워나감
    referee: RefereeDecision | None
    dice_check: DiceCheck | None
    recalled_memories: list[str]
    narration: str
    archivist: ArchivistOutput | None

    # 오류 처리
    error: str | None
```

## 5. 실패했을 때 (Fallback) — 반드시 설계해야 함

AI API는 **생각보다 자주 실패합니다.** (타임아웃, 429 한도초과, 서비스 장애)

| 어느 노드가 실패 | 대응 |
|---|---|
| 판정관 | 판정 없이 진행 (`needs_check = false`) |
| 이야기꾼 | 1회 재시도 → 또 실패하면 SSE `error` 이벤트, **턴을 저장하지 않음** |
| 기록원 | 상태 변화 없이 턴 저장 (서술은 살림). 경고 로그 |
| 어느 노드든 예외 | 세션 status를 `processing` → `active`로 **반드시 되돌림** |

> 🚨 **가장 위험한 버그**: 실패했는데 `processing`으로 남아버리면
> 그 세션은 **영원히 잠깁니다.** 유저는 아무것도 못 합니다.
> → `try / finally` 로 반드시 잠금을 풀어야 합니다.
> → 추가 안전장치: `processing`이 된 지 5분이 지났으면(`locked_at` 기준) 새 요청이 잠금을 가져갈 수 있음. (03번 문서 2-4의 SQL)

### 실패·중단 시 규칙 정리

| 상황 | DB | 유저가 받는 것 |
|---|---|---|
| 이야기꾼 2회 실패 | 턴 저장 안 함, 잠금 해제 | SSE `error` (`LLM_UNAVAILABLE`) |
| 기록원 실패 | 서술만 저장, 상태 변화 없음, 추천 행동 없음 | 정상 `turn_completed` (`state_patch`·`suggestions` 이벤트 없음) |
| 유저가 도중에 연결 끊음 | 저장 전이면 저장 안 함(잠금 해제), 저장 후면 저장됨 | 없음 (돌아오면 GET으로 복구, 04번 문서 7-7) |
| 서버가 처리 도중 죽음 | 트랜잭션 전이면 아무것도 안 남음 | 5분 뒤 잠금 자동 만료 |

> ⚠️ **DB 저장(트랜잭션) 도중에는 중단되지 않게** 보호합니다. (`asyncio.shield` 등)
> 반쯤 저장되는 일은 트랜잭션이 막아주지만, "저장은 됐는데 잠금 해제 전에 끊김" 같은 틈을 줄이기 위함입니다.

## 6. 비용 관리

| 노드 | 모델 등급 | 대략 비중 |
|---|---|---|
| 판정관 | 저가 | 5% |
| 이야기꾼 | 고성능 | 80% |
| 기록원 | 저가 | 10% |
| 임베딩 | 초저가 | 5% |

**절약 장치**
1. `summary_so_far` 요약을 써서 전체 대화 기록을 매번 보내지 않음
2. 프롬프트 캐싱 (시나리오 지시문 등 고정 부분)
3. `turns.token_usage`에 매 턴 기록 → 주간 비용 확인
4. 유저당 하루 턴 수 제한 (Step 11에서 도입)

## 8. 단계별 구현 순서 (한 번에 다 만들지 않음)

| Step | 만드는 노드 | 나머지는 |
|---|---|---|
| 6 | 이야기꾼만 (**응답 형식은 처음부터 SSE**, 서술은 한 덩어리로 1번 전송) | 판정/기억/기록원 전부 생략 |
| 7 | 이야기꾼 (토큰 단위 스트리밍 + heartbeat) | 〃 |
| 8 | + 판정관, 주사위, 기록원, 검증 | 기억 검색만 생략 |
| 9 | + 기억 검색 | 완성 |
| 10 | + NPC 에이전트 | 확장 |

> 💡 **처음부터 6개 노드를 다 만들면 어디서 틀렸는지 절대 못 찾습니다.**
> 한 노드씩 붙이고, 붙일 때마다 실제로 플레이해봅니다.

> 💡 **왜 Step 6부터 SSE 형식인가?** Step 6에서 일반 JSON으로 만들고 Step 7에서 SSE로 바꾸면,
> **프론트엔드는 같은 화면을 두 번 짜야 합니다.** 백엔드는 "AI 응답을 다 받은 뒤 한 번에 흘려보내기"로
> 시작하면 디버깅은 쉬우면서도 계약서 모양은 처음부터 최종 형태로 유지됩니다.

### 스트리밍 구현 힌트 (Step 7, 백엔드)
- LangGraph의 `astream(..., stream_mode=["messages", "custom"])`로 이야기꾼 노드의 토큰과 노드별 진행 신호를 받습니다.
- 받은 것을 04번 문서 7장 이벤트로 **번역하는 층(SSE 변환기)** 을 그래프 바깥에 따로 둡니다. (그래프는 SSE를 모름)
- heartbeat(15초)는 그래프와 별개로 도는 타이머가 보냅니다.
