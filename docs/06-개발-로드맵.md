## 진행 원칙 3가지

1. **"동작 확인 방법"을 통과하지 못하면 다음 Step으로 넘어가지 않는다.**
2. **한 Step이 끝나면 개발 로그를 쓴다.** (블로그 초안은 프로젝트 공부 세션 담당 — CLAUDE.md 5장)
3. **그 다음 커밋 + push 한다.** (되돌아갈 지점 만들기 + 다른 컴퓨터로 이어가기 — CLAUDE.md 6장)

> 순서는 항상 **① 동작 확인 → ② 개발 로그 → ③ 커밋·push** 입니다.
> 한 Step에 백엔드·프론트 작업이 둘 다 있으면, **각 세션이 자기 몫을 끝낼 때마다** 따로 개발 로그를 쓰고 커밋합니다.

| 할 일 | 누가 | 왜 |
|---|---|---|
| ① `frontend/.git` 폴더 삭제 | **사용자** (cmd, 프로젝트 루트에서 `rmdir /s /q frontend\.git`) | create-next-app이 만든 **빈 git 저장소**. 남겨두면 `frontend/` 안에서 친 git 명령이 진짜 저장소가 아니라 이 빈 저장소로 감. (커밋 0개라 지워도 손실 없음) |
| ② `frontend/.gitignore`에 `!.env.example` 추가 + `frontend/.env.example` 생성 (01번 문서 9장의 이름들, 값은 비움) | 프론트엔드 세션 | 지금은 `.env*` 규칙이 `.env.example`까지 막아서 다른 컴퓨터에서 필요한 환경변수 이름을 알 수 없음 |
| ③ `backend/requirements.txt` 버전 고정 (`>=` → `==`) | 백엔드 세션 | 컴퓨터마다 다른 버전이 깔리는 것 방지. 특히 LangChain/LangGraph는 1.0에서 크게 바뀜 |

- `frontend/.git` 폴더가 없다 / 프로젝트 루트에서 `git status`가 정상

- 새 가상환경에서 `pip install -r requirements.txt` 후 서버가 켜진다

## Step 2 — 로그인/인증 🔐

| 담당 | 양쪽 |
|---|---|

**프론트엔드**
1. `@supabase/supabase-js`, `@supabase/ssr` 설치
2. `.env.local`에 Supabase URL / publishable key
3. `/login` 페이지 — 이메일 회원가입/로그인
4. 로그인 안 한 상태로 보호된 페이지(`/characters`, `/play/...` 등) 접근 시 `/login`으로 보내기
   - ⚠️ Next.js 16에서는 파일 이름이 **`src/proxy.ts`** 입니다. (예전 강의·블로그의 `middleware.ts`는 옛 이름)
5. 로그아웃 버튼
6. ⚠️ 이 Step에서는 Supabase를 **로그인에만** 씁니다. `supabase.from(...)`으로 DB를 읽는 코드는 쓰지 않습니다. (01번 원칙 6)

**백엔드**
1. `PyJWT[crypto]` 설치 (버전 고정)
2. JWT 검증 의존성 `get_current_user` 구현 — JWKS로 서명 확인 + `aud="authenticated"` + `iss="<SUPABASE_URL>/auth/v1"` + 만료 확인. 실패 시 401 `UNAUTHORIZED`
3. `GET /api/v1/me` 구현 (프로필 없으면 생성 — 보조 안전장치)
4. CORS 설정 (04번 문서 9장, `CORS_ORIGINS` 환경변수)
5. 테스트용 토큰 발급 스크립트 `backend/scripts/get_test_token.py` (Supabase 비밀번호 로그인 API로 토큰을 받아 출력)
   → 프론트 없이도 Swagger UI(`/docs`)의 Authorize 버튼에 토큰을 넣어 테스트할 수 있게

**동작 확인**
- 회원가입 → Supabase Auth 대시보드에 유저가 보이고, `profiles`에도 한 줄 생긴다
- 로그아웃 상태로 `/characters` 주소를 치면 `/login`으로 이동한다
- 테스트 토큰으로 `GET /api/v1/me` → 200
- 토큰 없이 / 엉터리 토큰으로 → 401, 응답 모양이 `{"error": {...}}`

> ⚠️ **여기가 가장 많이 막히는 구간입니다.** JWT 검증은 비전공자에게 어렵습니다.
> 하루 안에 안 끝나도 정상입니다. 여기를 대충 넘기면 나중에 전부 다시 짜야 합니다.

## Step 3 — 타입 자동생성 + 목(mock) API 🔗

| 담당 | 양쪽 |
|---|---|

이 Step의 목적: **프론트가 백엔드를 기다리지 않고 일할 수 있게 만들기.**

**백엔드**
1. 04번 문서의 **모든 API를 Pydantic 모델로만** 정의 — **8장 모델 이름표 그대로**, 코드값은 `Literal`
2. 각 엔드포인트를 **가짜 데이터**를 돌려주는 껍데기로 구현
   - `GET /api/v1/meta/game-rules`는 가짜가 아니라 **진짜 규칙표**로 (02번 문서를 옮긴 파이썬 상수 `app/game/rules.py`)
   - `POST /sessions/{id}/actions`는 **가짜 SSE 스트림**(정해진 이벤트를 0.1초 간격으로 흘려보냄)으로 → 프론트가 SSE 파서를 미리 만들 수 있게
3. 전역 예외 처리기 3개 구현 (04번 문서 0장 — 422를 400으로, `{"detail"}`을 `{"error"}`로)
4. SSE 타입 문서용 엔드포인트 `GET /api/v1/_schema/sse-events` (04번 문서 8장)
5. `FastAPI(separate_input_output_schemas=False)` 설정 후 `/openapi.json` 확인

**프론트엔드**
1. `openapi-typescript` 설치 + `package.json`에 `"gen:api"` 스크립트 등록 → `npm run gen:api`
2. `src/types/index.ts` — 자동 생성 타입에 짧은 별명만 붙이기 (모양을 새로 정의하지 않음)
3. `src/lib/api-client.ts` — 토큰을 자동으로 붙이고, `{"error"}` 응답을 공통 처리하는 fetch 래퍼 (401이면 `/login`)
4. `src/lib/sse.ts` — SSE 파서 (04번 문서 7-4: 빈 줄 구분, `:` 주석 무시, `TextDecoder` stream 모드)
5. 생성된 타입으로 API 함수 작성

**동작 확인**
- 프론트에서 `getCharacters()`를 부르면 가짜 캐릭터 목록이 온다
- 가짜 행동 스트림을 받아 콘솔에 이벤트 7종이 순서대로 찍힌다
- 백엔드에서 Pydantic 필드명을 바꾸고 타입을 재생성하면, 프론트에서 **컴파일 에러가 난다** ← 이게 성공 신호

> 💡 **"에러가 나는 게 성공"인 이유**: 어긋남을 배포 전에 잡아준다는 뜻입니다.
> 이 장치가 없으면 어긋남을 **유저가 발견**합니다.

**동작 확인**: 행동을 입력하면 10초쯤 뒤에 GM 서술이 나온다. 전송 버튼을 연타해도 턴이 1개만 늘어난다. 새로고침해도 서술이 남아있다.

> 💡 **왜 토큰 스트리밍을 먼저 안 하나?** 스트리밍은 디버깅이 훨씬 어렵습니다.

> 💡 **그런데 왜 형식은 처음부터 SSE인가?** 여기서 JSON으로 만들면 Step 7에서 프론트가 같은 화면을 다시 짜야 합니다.
> "포장 상자(SSE 형식)는 처음부터 최종 모양, 내용물(한 덩어리 → 한 글자씩)만 나중에 바꾼다"는 전략입니다.
