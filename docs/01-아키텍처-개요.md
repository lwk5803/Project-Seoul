# 01. 아키텍처 개요

## 1. 한 줄 요약

> 💡 **유저가 "편의점에 들어간다"고 텍스트를 치면 →
> 서버의 AI 게임마스터가 주사위를 굴리고 이야기를 지어내서 →

## 3. 각 부품이 하는 일 (비유)

| 부품 | 비유 | 실제 역할 |
|---|---|---|
| **Next.js** | 게임기 화면과 컨트롤러 | 유저에게 보여주고, 입력을 받아 서버로 보냄 |
| **Supabase Auth** | 신분증 발급소 | 로그인 처리, "이 사람 진짜 회원 맞음" 도장(JWT) 찍어줌 |
| **FastAPI** | 게임 마스터의 책상 | 규칙 판정, AI 호출, 저장 — 모든 판단이 여기서 일어남 |
| **LangGraph** | 여러 명의 보조 진행자 팀 | 규칙 판정자 / 이야기꾼 / 기록원이 순서대로 일함 |
| **PostgreSQL** | 게임 기록장 | 캐릭터 시트, 지금까지 있었던 일 전부 |
| **pgvector** | GM의 "기억 서랍" | "3시간 전에 만난 그 NPC 이름이 뭐였지?"를 찾아줌 |
| **LangSmith** | CCTV | AI가 왜 그렇게 답했는지 나중에 되돌려 봄 |

## 4. 절대 지켜야 할 설계 원칙 6가지

이 6가지가 **버그의 90%를 미리 막는 규칙**입니다.

### 원칙 1. 주사위는 AI가 굴리지 않는다 🎲

AI에게 "주사위 굴려줘"라고 하면 AI는 **자기가 원하는 숫자**를 말합니다.
(AI는 난수 생성기가 아니라 "그럴듯한 말을 만드는 기계"이기 때문입니다.)

```
❌ 나쁜 방식: AI야, 주사위 굴려서 성공인지 판단해줘
✅ 좋은 방식: 파이썬이 random으로 17을 굴림 → "17 나왔고 성공이야. 이걸 소설처럼 묘사해줘"
```

**판정은 파이썬 코드, 묘사는 AI.** 이 경계를 절대 넘지 않습니다.

### 원칙 2. 게임 상태의 주인은 DB다 💾

AI가 "HP를 20 깎겠습니다"라고 **제안**은 할 수 있지만,
실제로 깎는 것은 파이썬 코드입니다. 파이썬이 검증합니다.

```
AI 제안: { "hp": -20 }
   ↓
파이썬 검증: HP가 0 밑으로 안 내려가나? 한 턴에 -20은 너무 큰가? (상한선 체크)
   ↓
DB 반영: hp = max(0, 현재HP - 20)
```

> 이게 없으면 AI가 "당신은 갑자기 100억을 얻었습니다"라고 하고
> 실제로 소지금이 100억이 되는 사고가 납니다.

### 원칙 3. 타입은 자동으로 맞춘다 🔗

프론트엔드가 `character.hp`를 기대하는데 백엔드가 `character.health`를 보내면 화면이 깨집니다.
이 문제를 **사람의 주의력**으로 막으면 반드시 실패합니다.

```
백엔드 Pydantic 모델 → FastAPI가 OpenAPI 문서 자동 생성 → 프론트가 TypeScript 타입 자동 생성
```

**프론트엔드는 API 응답 타입을 손으로 적지 않습니다.** (Step 3에서 구축)

### 원칙 4. 모든 오류는 같은 모양으로 🚨

```json
{ "error": { "code": "SESSION_NOT_FOUND", "message": "게임 세션을 찾을 수 없습니다.", "detail": null } }
```

프론트엔드는 `error.code`만 보고 화면 처리를 결정합니다.
(`message`는 유저에게 그대로 보여줘도 되는 한글 문장입니다.)

### 원칙 5. 같은 요청을 두 번 보내도 턴은 하나만 🔁

인터넷이 끊겼다 다시 연결되면 브라우저가 같은 요청을 두 번 보낼 수 있습니다.
그러면 턴이 두 번 진행되고 HP가 두 번 깎입니다.

→ 프론트가 요청마다 `client_action_id`(고유 번호)를 붙이고,
   백엔드는 **이미 본 번호면 기존 결과를 그대로 돌려줍니다.** (04번 문서 7-2)

### 원칙 6. 프론트는 DB를 직접 만지지 않는다 🚪

```
✅ 브라우저 → Supabase Auth      (로그인/회원가입만)
✅ 브라우저 → FastAPI → DB       (게임 데이터는 전부 이 길로)
❌ 브라우저 → Supabase DB 직접   (supabase.from('characters') 같은 코드 금지)
```

> 💡 **은행 창구 비유**: 손님은 금고에 직접 들어가지 않고 창구 직원에게 요청합니다.
> 프론트가 DB를 직접 읽고 쓰기 시작하면, 백엔드의 검증(합계 15, 상한 clamp, 턴 잠금)을 **건너뛰는 뒷문**이 생깁니다.
> 그래서 DB 보안 정책(RLS)도 "브라우저는 아무것도 못 쓴다"로 잠가둡니다. (03번 문서 3장)

## 5. 한 턴이 처리되는 전체 흐름

```
[유저] "편의점 알바생에게 어제 있었던 일을 물어본다"
   │
   ▼
[프론트] POST /api/v1/sessions/{id}/actions
         { client_action_id: "uuid...", content: "편의점 알바생에게..." }
   │
   ▼
[백엔드] ① JWT 검증 — 이 사람이 이 세션의 주인이 맞나?
         ② 중복 요청 검사 — client_action_id 이미 있나?
         ③ 턴 잠금 — 이 세션이 이미 처리 중이면 409 반환
   │
   ▼
[LangGraph 실행]
   ├─ (1) 판정관 노드: "설득 판정 필요, 매력 능력치, 난이도 14"  ← AI가 결정
   ├─ (2) 주사위 노드: 1d20 = 11, +매력(3)×2=6 → 총 17 ≥ 14 → 성공  ← 파이썬이 계산
   ├─ (3) 기억 검색 노드: pgvector에서 "알바생" 관련 과거 장면 3개 회수
   ├─ (4) 이야기꾼 노드: 위 정보 전부 받아서 서술 생성 (스트리밍)  ← AI
   └─ (5) 기록원 노드: 상태 변화 추출 + 장면 요약 저장  ← AI 제안 + 파이썬 검증
   │
   ▼
[백엔드 → 프론트] SSE 스트림으로 실시간 전송 (04번 문서 7장)
         turn_started → dice_roll → narration_delta×N → state_patch → suggestions → turn_completed
         (조용한 구간에는 15초마다 heartbeat)
   │
   ▼
[프론트] 이야기가 한 글자씩 타이핑, 우측 상태창의 HP/멘탈/소지금 갱신
```

## 6. 왜 SSE인가? (WebSocket이 아니라)

| 방식 | 설명 | 우리에게 맞나 |
|---|---|---|
| 일반 HTTP | 다 만들어질 때까지 기다렸다가 한 번에 받음 | ❌ AI 응답은 10초씩 걸림. 빈 화면 10초는 최악 |
| **SSE** | 서버→클라이언트 한 방향으로 조금씩 흘려보냄 | ✅ TRPG는 "내가 말하고 → GM이 답한다"의 반복. 한 방향이면 충분 |
| WebSocket | 양방향 실시간 | ⚠️ 여러 명이 동시에 플레이하는 멀티플레이가 되면 필요. 지금은 과함 |

> 💡 **SSE = 라디오 방송**. 방송국(서버)이 계속 말하고 청취자(브라우저)는 듣기만 합니다.
> WebSocket = 전화 통화. 양쪽이 동시에 말할 수 있지만 그만큼 관리가 복잡합니다.

**결론: 1인 플레이 MVP는 SSE. 멀티플레이로 확장할 때 WebSocket 재검토.**

## 7. 배포 구조

| 대상 | 서비스 | 이유 |
|---|---|---|
| Next.js | Vercel | Next.js 만든 회사. 설정 거의 0 |
| FastAPI | Render (또는 Railway) | 무료 티어 존재. Docker 없이도 배포 가능 |
| DB/Auth | Supabase | 이미 채택 |

⚠️ **주의: Render 무료 티어는 15분간 요청이 없으면 서버가 잠듭니다.**
잠든 서버를 깨우는 데 30초~1분이 걸려서, 첫 요청이 타임아웃됩니다.
→ Step 11에서 "서버 깨우는 중입니다" 로딩 화면을 프론트에 넣어야 합니다. (미리 계획된 대응)

## 8. 확정된 기술 결정 (한눈에 보기)

> 💡 **"이미 정한 것"을 한곳에 모아둔 표입니다.** 각 세션은 여기와 다르게 구현하지 않습니다.
> 바꾸고 싶으면 아키텍처 세션에 요청합니다.

| 영역 | 결정 | 이유 | 자세히 |
|---|---|---|---|
| 백엔드 DB 접속 | **psycopg 3 (비동기) + 커넥션 풀**, Supabase **Session pooler** 주소 | 턴 저장을 트랜잭션으로 묶어야 함. pooler는 IPv4라 로컬·배포 공통 | 03번 6장 |
| `supabase` 파이썬 라이브러리 | 게임 데이터에 **사용 안 함** | REST 방식은 트랜잭션 불가 | 03번 6장 |
| JWT 검증 | **PyJWT + JWKS**(Supabase 공개키 목록). `aud="authenticated"`, `iss="<SUPABASE_URL>/auth/v1"` 확인 | 비밀키를 백엔드에 두지 않고 서명 확인 | 06번 Step 2 |
| 프로필 생성 | **DB 트리거**(가입 즉시) + `/me` 보조 | 호출 순서 의존 제거 | 03번 2-1 |
| 프론트 ↔ 백엔드 | 브라우저가 FastAPI **직접 호출**, `Authorization: Bearer` | 구조 단순. Next.js 서버 경유 없음 | 04번 0장 |
| 행동 스트림 | **자체 SSE 규격**, 프론트는 `fetch` + `ReadableStream`으로 파싱 | `EventSource`는 헤더 불가 | 04번 7장 |
| Vercel AI SDK | **행동 스트림에는 사용 안 함** | AI SDK의 `useChat`은 자기만의 스트림 형식을 요구해서 우리 SSE 규격과 맞지 않음 | — |
| 로그인 페이지 보호 | Next.js 16의 **`proxy.ts`** (예전 이름 `middleware.ts`) | Next.js 16에서 이름이 바뀜 | 06번 Step 2 |
| 타입 공유 | Pydantic → OpenAPI → `openapi-typescript`, **SSE 타입까지 자동** | 사람이 맞추면 반드시 어긋남 | 04번 8장 |
| 라이브러리 버전 | 백엔드 `requirements.txt`는 **`==`로 고정**, 프론트는 `package-lock.json` 커밋 | 데스크톱/노트북 버전 차이 방지 | 06번 Step 0.5 |
| 기억 검색 | pgvector, 세션 안에서만 검색, **전용 인덱스 없음(MVP)** | 세션당 기억 수가 적음 | 03번 4장 |
| AI 모델 | **미정 (가정: OpenAI)** — 코드는 모델 이름을 환경변수로 받게 짬 | 계속 바꿔가며 실험 예정 | 08번 ② |

## 9. 환경변수 이름표 (⚠️ 이 이름 그대로)

> 💡 환경변수 = 코드 밖에 두는 설정값(비밀번호, 주소 등). 이름이 세션마다 다르면 "왜 값이 비어있지?" 지옥이 됩니다.
> 실제 값은 `.env` / `.env.local`에만 쓰고(커밋 금지), **이름 목록은 `.env.example`에 적어 커밋**합니다.

### 백엔드 `backend/.env`

| 이름 | 예시/설명 | 필요 시점 |
|---|---|---|
| `SUPABASE_URL` | `https://xxxx.supabase.co` | Step 2 |
| `SUPABASE_JWKS_URL` | `https://xxxx.supabase.co/auth/v1/.well-known/jwks.json` | Step 2 |
| `SUPABASE_PUBLISHABLE_KEY` | 테스트 토큰 발급 스크립트(`scripts/get_test_token.py`) 전용. 서버 코드에서는 안 씀 | Step 2 |
| `DATABASE_URL` | Session pooler 연결 문자열 (`postgresql://postgres.xxxx:<비밀번호>@...pooler.supabase.com:5432/postgres`) | Step 1 |
| `CORS_ORIGINS` | `http://localhost:3000` (쉼표로 여러 개) | Step 2 |
| `OPENAI_API_KEY` | (AI 제공자 확정 후) | Step 6 |
| `LLM_NARRATOR_MODEL` / `LLM_FAST_MODEL` | 이야기꾼용 / 판정관·기록원용 모델 이름 | Step 6 |
| `EMBEDDING_MODEL` | 임베딩 모델 이름 | Step 9 |
| `LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY` / `LANGCHAIN_PROJECT` | LangSmith | Step 6 |

- 기존 `SUPABASE_SECRET_KEY` / `SUPABASE_DB_PASSWORD`는 위 결정으로 **백엔드 서버에서 쓰지 않게 됩니다.**
  → Step 1에서 백엔드 세션이 `config.py`와 `.env.example`을 위 표에 맞게 정리합니다.
  (`DB_PASSWORD`는 `DATABASE_URL` 안에 포함됨)
- ⚠️ 백엔드 서버는 **`backend/` 폴더 안에서** 실행합니다. (`config.py`가 현재 폴더의 `.env`를 읽기 때문)

### 프론트엔드 `frontend/.env.local`

| 이름 | 예시/설명 | 필요 시점 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://xxxx.supabase.co` | Step 2 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Supabase publishable key (`sb_publishable_...`) | Step 2 |
| `NEXT_PUBLIC_API_BASE_URL` | `http://localhost:8000` | Step 3 |

- ⚠️ `NEXT_PUBLIC_`으로 시작하는 값은 **브라우저에 그대로 노출**됩니다. 비밀키(secret key, DB 비밀번호)는 절대 여기 넣지 않습니다.
