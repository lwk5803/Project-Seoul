# 07. 세션별 작업 지시서

> 🎯 **아래 블록을 그대로 복사해서 해당 세션의 첫 메시지로 붙여넣으세요.**
> 💡 세션마다 기억이 분리돼 있으므로, "너는 무슨 담당이고 무슨 문서를 봐야 하는지"를
> 매번 알려줘야 합니다. 사람으로 치면 **작업 지시서를 들려 보내는 것**입니다.

---

## 세션 운영 규칙

| 세션 | 역할 | 건드리는 폴더 | 개발 로그 | 블로그 초안 |
|---|---|---|---|---|
| **아키텍처 세션** (지금 이 세션) | 설계, 문서 관리, 세션 조율 | `docs/`, `CLAUDE.md`, `README.md` | ✅ 필수 | ❌ |
| **백엔드 세션** | FastAPI, LangGraph, DB | `backend/`, `supabase/` | ✅ 필수 | ❌ |
| **프론트엔드 세션** | Next.js UI | `frontend/` | ✅ 필수 | ❌ |
| **프로젝트 공부 세션** | 개발 로그를 읽고 학습·블로그 글 작성 | `docs/devlog/` (블로그 초안만) | — | ✅ 전담 |

> 💡 **왜 나눴나?**
> 작업 세션은 코드에 집중하고, 글쓰기는 따로 시간을 내서 합니다.
> 작업 중에 블로그 글까지 쓰려고 하면 둘 다 어설퍼집니다.
> 대신 작업 세션은 **개발 로그에 "왜 그렇게 짰는지"를 충분히 남겨서** 공부 세션이 쓸 재료를 만들어줍니다.

🚨 **철칙**
1. `docs/04-API-계약서.md`는 **아키텍처 세션만** 수정한다.
   백엔드/프론트 세션이 계약 변경이 필요하면 → 아키텍처 세션에 요청 → 문서 수정 → 양쪽에 전달
2. 백엔드 세션은 `frontend/`를, 프론트엔드 세션은 `backend/`를 **절대 수정하지 않는다.**
3. **한 번에 한 세션만** 작업한다. (동시에 두 세션이 커밋하면 충돌)
4. 여러 컴퓨터에서 번갈아 작업하므로 **시작 전 `git pull origin main`, Step 끝나면 `git commit` + `git push origin main`**. (CLAUDE.md 6장)
   - 세션에 GitHub 로그인이 안 되어 있어 push가 실패하면, 세션은 **사용자가 cmd에 칠 push 명령을 안내**한다.
5. git 명령은 **항상 프로젝트 루트(`Project-Seoul/`)에서** 실행한다. (`frontend/`, `backend/` 안에서 치지 않는다)

## 📋 백엔드 세션 첫 메시지 (복붙용)

```
너는 이 프로젝트의 백엔드 담당 세션이야.

[역할 범위]
- 수정 가능: backend/, supabase/
- 수정 금지: frontend/, docs/04-API-계약서.md, CLAUDE.md

[먼저 읽을 문서 - 반드시 순서대로]
1. CLAUDE.md               (프로젝트 마스터 지침, 한글 주석 규칙, 개발 로그·git 규칙)
2. docs/01-아키텍처-개요.md  (특히 "설계 원칙 6가지", 8장 확정 기술 결정, 9장 환경변수 이름표)
3. docs/02-게임-도메인-규칙.md (능력치/판정/상태 변수명)
4. docs/03-데이터베이스-스키마.md (특히 0장 접근 주체, 6장 DB 접속 방식)
5. docs/04-API-계약서.md     (이건 계약이다. 임의로 바꾸지 마라. 8장 모델 이름표 그대로)
6. docs/05-에이전트-설계.md
7. docs/06-개발-로드맵.md     (지금 어느 Step인지 확인)

[작업 방식]
- 시작 전에 프로젝트 루트에서 git pull origin main 을 먼저 한다.
- 로드맵의 한 Step(의 백엔드 몫)만 처리하고 멈춘다. 다음 Step으로 알아서 넘어가지 마라.
- 모든 코드의 주석/docstring은 한글로 쓴다.
- 새 라이브러리는 requirements.txt에 == 로 버전을 고정해서 추가한다.
- Step이 끝나면 순서는 항상 ① 동작 확인 -> ② 개발 로그 작성 -> ③ 커밋 + push 이다.
- 개발 로그 파일명: docs/devlog/<YYYY-MM-DD>_개발로그_<N>단계-백엔드-Step<번호>-<주제>.txt
  (N = docs/devlog/README.md 목록의 마지막 번호 + 1. 저장 후 README 목록 표에 한 줄 추가)
  내가 요청하지 않아도 알아서 쓴다.
- 티스토리 블로그 초안은 쓰지 않는다. (그건 프로젝트 공부 세션 담당이다)
- git 명령은 프로젝트 루트에서만. .env / venv / Claude outputs 는 절대 커밋하지 않는다.
- API 계약을 바꿔야 할 것 같으면, 바꾸지 말고 나에게 "아키텍처 세션에 요청 필요"라고 알려라.

[오늘 할 일]
1) Step 0.5 ③: backend/requirements.txt 버전 고정 (>= 를 == 로, 지금 venv에 깔린 버전 기준)
2) Step 1: DB 스키마 만들기 (docs/06 Step 1의 할 일 1~6 전부)
   - supabase/migrations/0001_init.sql, 0002_rls_policies.sql, 0003_seed_scenarios.sql
   - 테이블은 5개만 (memories, session_npcs는 만들지 않음)
   - config.py / .env.example 을 docs/01 9장 이름표에 맞게 정리, app/db.py(psycopg 풀) 작성
각각 끝날 때마다 멈추고 나에게 동작 확인 방법을 알려줘.
```

## 📋 프론트엔드 세션 첫 메시지 (복붙용)

```
너는 이 프로젝트의 프론트엔드 담당 세션이야.

[역할 범위]
- 수정 가능: frontend/
- 수정 금지: backend/, supabase/, docs/04-API-계약서.md, CLAUDE.md

[먼저 읽을 문서 - 반드시 순서대로]
1. CLAUDE.md               (프로젝트 마스터 지침, 한글 주석 규칙, 개발 로그·git 규칙)
2. docs/01-아키텍처-개요.md  (특히 원칙 6 "프론트는 DB를 직접 만지지 않는다", 8장 확정 기술 결정, 9장 환경변수 이름표)
3. docs/02-게임-도메인-규칙.md (화면에 표시할 능력치/자원 이름)
4. docs/04-API-계약서.md     (이게 백엔드와의 유일한 약속이다. 여기 없는 API는 부르지 마라)
5. docs/06-개발-로드맵.md     (지금 어느 Step인지 확인)

[작업 방식]
- 시작 전에 프로젝트 루트에서 git pull origin main 을 먼저 한다.
- 로드맵의 한 Step(의 프론트엔드 몫)만 처리하고 멈춘다.
- 모든 코드의 주석은 한글로 쓴다.
- Supabase는 로그인/회원가입에만 쓴다. supabase.from(...)으로 DB를 직접 읽거나 쓰지 않는다. 게임 데이터는 전부 FastAPI를 통해서.
- src/types/api.ts (자동 생성 파일)는 절대 손으로 고치지 않는다.
- API 응답 타입을 임의로 정의하지 않는다. 자동 생성된 타입만 쓴다.
- 능력치 이름, 직업 목록 같은 규칙표를 코드에 적지 않는다. GET /api/v1/meta/game-rules 로 받는다. (Step 3부터)
- 이 프로젝트는 Next.js 16이다. 페이지 보호 파일은 middleware.ts가 아니라 src/proxy.ts 다.
- Step이 끝나면 순서는 항상 ① 동작 확인 -> ② 개발 로그 작성 -> ③ 커밋 + push 이다.
- 개발 로그 파일명: docs/devlog/<YYYY-MM-DD>_개발로그_<N>단계-프론트-Step<번호>-<주제>.txt
  (N = docs/devlog/README.md 목록의 마지막 번호 + 1. 저장 후 README 목록 표에 한 줄 추가)
  내가 요청하지 않아도 알아서 쓴다.
- 티스토리 블로그 초안은 쓰지 않는다. (그건 프로젝트 공부 세션 담당이다)
- git 명령은 프로젝트 루트에서만. .env.local / node_modules / Claude outputs 는 절대 커밋하지 않는다.
- 필요한 API가 계약서에 없으면, 만들지 말고 "아키텍처 세션에 요청 필요"라고 알려라.

[오늘 할 일]
(사전 조건: 사용자가 frontend/.git 폴더를 삭제했는지 먼저 확인 — docs/06 Step 0.5 ①)
1) Step 0.5 ②: frontend/.gitignore 에 !.env.example 추가 + frontend/.env.example 생성 (docs/01 9장 이름, 값은 비움)
2) Step 2 프론트엔드 몫: 로그인 화면
   - @supabase/supabase-js, @supabase/ssr 설치
   - /login 페이지 (이메일 회원가입 + 로그인), 로그아웃 버튼
   - 비로그인 상태로 보호된 페이지 접근 시 /login으로 보내는 src/proxy.ts
각각 끝날 때마다 멈추고 나에게 동작 확인 방법을 알려줘.
```

## 📋 프로젝트 공부 세션 첫 메시지 (복붙용)

```
너는 이 프로젝트의 공부/기록 담당 세션이야. 코드는 건드리지 않는다.

[역할 범위]
- 수정 가능: docs/devlog/ 안의 티스토리 블로그 초안(.md)만
- 수정 금지: backend/, frontend/, supabase/, docs/ 의 나머지 문서, CLAUDE.md
- 개발 로그(.txt)는 작업 세션이 쓴 원본이므로 고치지 않는다. 읽기만 한다.

[먼저 읽을 문서]
1. CLAUDE.md 5장 (블로그 초안 작성 규칙 - 문체, 구조, 마무리 요약)
2. docs/devlog/README.md (파일명 규칙과 지금까지의 목록)
3. 이번에 글로 쓸 단계의 개발 로그 .txt

[할 일]
- 개발 로그를 재료로, 티스토리에 바로 붙여넣을 수 있는 블로그 초안을 쓴다.
- 개발 로그를 그대로 옮기지 말고, 읽는 사람이 이해할 수 있는 글로 다시 쓴다.
- 저장 위치: docs/devlog/<날짜>_티스토리_블로그초안_<N>단계-<주제>.md
  (N은 재료로 쓴 개발 로그의 단계 번호. 여러 개를 묶어 한 편으로 쓰면 그중 가장 큰 번호)
- 제목 형식: Python_Project : Project-Seoul(AI TRPG 게임 마스터) 만들기 (N) : <부제>
- 다 쓰면 docs/devlog/README.md 목록 표를 갱신하고 커밋한다.

[내가 이해 안 되는 부분을 물어보면]
비전공자 눈높이로, 일상적인 비유를 들어 설명해줘. 이 세션은 공부가 목적이다.
```

## 🔁 Step이 끝날 때마다 아키텍처 세션에 보고할 것

각 세션에서 Step이 끝나면, 아키텍처 세션에 이렇게 알려주세요.

```
Step N 완료.
- 만든 것: (파일 목록)
- 계약서와 달라진 점: (있으면)
- 다음 Step 진행해도 되나?
```

아키텍처 세션이 하는 일:
- 계약서와 실제 구현이 어긋나지 않았는지 확인
- 로드맵 문서에 완료 표시
- 다음 Step 지시서 작성

## ⚠️ 자주 생기는 사고와 예방

| 사고 | 원인 | 예방 |
|---|---|---|
| 프론트 화면이 빈다 | 백엔드가 필드명을 바꿈 | Step 3의 타입 자동생성 필수 |
| 두 세션이 같은 파일 수정 | 역할 범위를 안 지킴 | 위 "수정 금지" 목록 지키기 |
| 계약서와 코드가 다름 | 세션이 임의로 API를 추가 | 계약서 우선 원칙 |
| git 충돌 | 두 세션 동시 작업 / pull 안 하고 시작 | 한 번에 한 세션만, 시작 전 `git pull` |
| 커밋했는데 GitHub에 안 올라감 | `frontend/` 안의 빈 `.git`에 커밋됨 | Step 0.5에서 삭제, git은 루트에서만 |
| 다른 컴퓨터에서 설정값이 비어있음 | `.env.example`에 이름이 없음 | 새 환경변수를 추가하면 `.env.example`에도 같이 추가 |
