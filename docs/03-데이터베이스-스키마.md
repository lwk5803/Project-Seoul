# 03. 데이터베이스 스키마 (Supabase / PostgreSQL)

> 🎯 **DB = 게임의 기록장**.
> 서버가 꺼졌다 켜져도, 브라우저를 닫았다 열어도
> 여기 적힌 것만 살아남습니다.

---

## 1. 테이블 전체 지도

```
auth.users (Supabase가 자동 관리 — 우리가 손대지 않음)
   │
   └─< profiles          (닉네임 등 추가 정보)
         │
         ├─< characters      (캐릭터 시트)
         │
         └─< game_sessions   (게임 한 판)
               │   └─ scenario_id ──> scenarios (시나리오 원본)
               │
               ├─< turns      (턴 기록 = 대화 로그)
               │     │
               │     └─< memories  (장기 기억, pgvector)
               │
               └─< session_npcs (이 판에 등장한 NPC 상태)
```

`─<` 표시는 "1:N 관계"입니다. (프로필 1개에 캐릭터 여러 개)

---

## 2. 테이블 상세

### 2-1. `profiles` — 유저 추가 정보

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | `auth.users.id`와 동일 (FK) |
| `nickname` | text | 표시 이름 |
| `created_at` | timestamptz | 가입 시각 |

> 💡 **왜 `auth.users`를 그대로 안 쓰나?**
> Supabase의 `auth.users`는 우리가 컬럼을 추가할 수 없는 "잠긴 표"입니다.
> 그래서 같은 id를 가진 우리 표를 하나 더 만들어 붙입니다. (업계 표준 패턴)

### 2-2. `characters` — 캐릭터 시트

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK→profiles | 주인 |
| `name` | text | 캐릭터 이름 |
| `occupation` | text | 직업 코드 (02번 문서 6장) |
| `background` | text | 유저가 쓴 배경 설정 (최대 500자) |
| `stats` | jsonb | `{"strength":2,"agility":3,...}` |
| `created_at` | timestamptz | |

⚠️ `hp` / `money` 는 여기 **없습니다.** 캐릭터는 "설계도"이고,
실제 체력은 게임 세션마다 달라지므로 `game_sessions`에 있습니다.
(같은 캐릭터로 여러 판을 할 수 있게 하기 위함)

### 2-3. `scenarios` — 시나리오 원본

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `title` | text | "을지로 3가의 실종자" |
| `summary` | text | 목록에 보여줄 2~3줄 소개 |
| `opening_narration` | text | 게임 시작 시 나오는 첫 서술 (AI 호출 없이 고정) |
| `initial_world_state` | jsonb | 시작 위치, 시간, 날씨 등 |
| `gm_guideline` | text | AI에게 주는 톤/분위기 지시문 |
| `goal_flags` | jsonb | 클리어 조건 `{"found_missing_person": true}` |
| `is_public` | boolean | 목록 노출 여부 |

> 💡 `opening_narration`을 고정 텍스트로 둔 이유:
> 게임 시작 버튼을 눌렀을 때 AI를 기다리면 10초가 걸립니다.
> 첫인상이 "로딩"이면 안 됩니다. 첫 장면은 미리 써둡니다.

### 2-4. `game_sessions` — 게임 한 판

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | |
| `character_id` | uuid FK | |
| `scenario_id` | uuid FK | |
| `status` | text | `active` / `processing` / `ended_victory` / `ended_defeat` / `ended_by_user` / `ended_timeout` |
| `turn_count` | int | 현재까지 진행된 턴 수 |
| `resources` | jsonb | `{"hp":88,"max_hp":100,"mental":72,"max_mental":100,"money":250000,"inventory":[...]}` |
| `world_state` | jsonb | 02번 문서 5장 형식 |
| `summary_so_far` | text | 지금까지 줄거리 요약 (AI가 10턴마다 갱신) |
| `created_at` / `updated_at` | timestamptz | |

#### ⚠️ `status = 'processing'`의 역할 (턴 잠금)

유저가 전송 버튼을 연타하면 턴이 여러 개 동시에 처리되어 상태가 엉킵니다.

```
행동 요청 도착
  → status를 'active' → 'processing' 으로 바꾼다 (조건부 UPDATE)
  → 못 바꿨다? = 누가 이미 처리 중 = 409 에러 반환
  → 처리 끝나면 다시 'active'로
```

> 💡 **화장실 문의 "사용중" 표시**와 같습니다. 한 번에 한 명만.

### 2-5. `turns` — 턴 기록 (대화 로그)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK | |
| `turn_number` | int | 1부터 |
| `client_action_id` | uuid | **UNIQUE(session_id, client_action_id)** — 중복 방지 |
| `player_input` | text | 유저가 친 행동 |
| `dice_check` | jsonb NULL | 판정 정보. 판정 없으면 null |
| `narration` | text | GM 서술 |
| `state_patch` | jsonb | 이 턴에 실제 반영된 변화 |
| `suggestions` | jsonb | 추천 행동 3개 (문자열 배열) |
| `token_usage` | jsonb | `{"input":1200,"output":430}` — 비용 추적용 |
| `latency_ms` | int | 응답 소요 시간 |
| `created_at` | timestamptz | |

> 💡 `token_usage`를 처음부터 기록하는 이유:
> AI API는 쓴 만큼 돈이 나갑니다. 나중에 "왜 이번 달 20만원 나왔지?"를
> 추적하려면 턴별 기록이 있어야 합니다. 나중에 추가하면 과거 데이터가 없습니다.

### 2-6. `memories` — 장기 기억 (pgvector)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK | |
| `turn_id` | uuid FK | 어느 턴에서 나온 기억인지 |
| `content` | text | "주인공은 편의점에서 김수진에게 실종자 사진을 보여줬다" |
| `embedding` | vector(1536) | 의미를 숫자로 바꾼 것 |
| `importance` | int | 1~5. 중요한 사건일수록 높게 |
| `created_at` | timestamptz | |

> 💡 **임베딩이 뭔가요?**
> 문장의 "의미"를 1536개의 숫자로 바꾼 좌표입니다.
> 비슷한 의미의 문장은 좌표가 가깝습니다.
> 그래서 "알바생"으로 검색하면 "김수진"이 나온 장면도 찾아집니다.
> **키워드가 아니라 의미로 찾는 검색**입니다.

⚠️ `vector(1536)`은 OpenAI `text-embedding-3-small` 기준입니다.
**임베딩 모델을 바꾸면 차원 수가 달라져서 테이블을 다시 만들어야 합니다.**
→ 08번 문서에서 모델을 먼저 확정해야 하는 이유.

### 2-7. `session_npcs` — 등장 NPC 상태

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK | |
| `name` | text | "김수진" |
| `persona` | text | 성격/말투 설정 |
| `disposition` | int | -5(적대) ~ +5(호의) |
| `notes` | text | 이 NPC가 기억하는 것 |

## 3. 보안: RLS (Row Level Security)

> 🚨 **이것을 빼먹으면 A유저가 B유저의 캐릭터를 볼 수 있습니다.**
> Supabase에서 가장 흔한 사고입니다.

RLS = "표의 각 줄마다 자물쇠를 다는 것"입니다.

```sql
-- 모든 게임 테이블에 켠다
alter table characters enable row level security;

-- "내 것만 보이고, 내 것만 고칠 수 있다"
create policy "본인 캐릭터만 조회" on characters
  for select using (auth.uid() = user_id);

create policy "본인 캐릭터만 생성" on characters
  for insert with check (auth.uid() = user_id);
```

- `scenarios`만 예외: `is_public = true`면 누구나 조회 가능
- 백엔드는 `secret key`를 쓰므로 RLS를 우회합니다.
  → **백엔드 코드가 직접 `user_id`를 검사해야 합니다.** (원칙: 이중 잠금)

## 4. 인덱스 (속도)

```sql
create index on turns (session_id, turn_number desc);   -- 최근 턴 빠르게 조회
create index on game_sessions (user_id, updated_at desc); -- 내 세션 목록
create index on memories using ivfflat (embedding vector_cosine_ops); -- 의미 검색
```

## 5. 마이그레이션 관리 방식

```
supabase/migrations/
  0001_init.sql          ← 테이블 생성
  0002_rls_policies.sql  ← 보안 정책
  0003_seed_scenarios.sql ← 시나리오 샘플 데이터
```
