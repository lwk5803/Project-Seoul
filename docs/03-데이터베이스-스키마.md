# 03. 데이터베이스 스키마 (Supabase / PostgreSQL)

> 🎯 **DB = 게임의 기록장**.
> 서버가 꺼졌다 켜져도, 브라우저를 닫았다 열어도
> 여기 적힌 것만 살아남습니다.

---

## 0. 누가 DB에 접근하나 (⚠️ 먼저 읽기)

| 누가 | 어떻게 | 무엇을 |
|---|---|---|
| **FastAPI 백엔드** | Postgres **직접 연결** (psycopg, 6장) | 모든 게임 테이블 읽기/쓰기 |
| **프론트엔드(브라우저)** | Supabase Auth만 사용 | 로그인/회원가입만. **게임 테이블은 절대 직접 조회하지 않음** |

> 💡 **은행 창구 비유**: 손님(브라우저)은 금고(DB)에 직접 들어가지 않고
> 창구 직원(FastAPI)에게 요청합니다. 창구 직원이 규칙을 확인한 뒤 금고를 엽니다.
> 프론트가 `supabase.from('characters')`로 DB를 직접 읽기 시작하면
> 백엔드의 검증(합계 15, 상한 clamp 등)을 건너뛰는 뒷문이 생깁니다.

## 1. 테이블 전체 지도

```
auth.users (Supabase가 자동 관리 — 우리가 손대지 않음)
   │   └─ (가입 순간 트리거가 profiles 한 줄 자동 생성)
   │
   └─< profiles          (닉네임 등 추가 정보)
         │
         ├─< characters      (캐릭터 시트, 삭제 시 "삭제 표시"만)
         │
         └─< game_sessions   (게임 한 판)
               │   └─ scenario_id ──> scenarios (시나리오 원본)
               │
               ├─< turns      (턴 기록 = 대화 로그)
               │     │
               │     └─< memories  (장기 기억, pgvector, Step 9)
               │
               └─< session_npcs (이 판에 등장한 NPC 상태, Step 10)
```

`─<` 표시는 "1:N 관계"입니다. (프로필 1개에 캐릭터 여러 개)

## 2. 테이블 상세

> 모든 테이블 공통: `id uuid PK default gen_random_uuid()`, 시각은 `timestamptz`(UTC 저장).

### 2-1. `profiles` — 유저 추가 정보

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | `auth.users.id`와 동일 (FK, `on delete cascade`) |
| `nickname` | text not null | 표시 이름. 기본값 = 이메일의 `@` 앞부분 |
| `created_at` | timestamptz | 가입 시각 |

> 💡 **왜 `auth.users`를 그대로 안 쓰나?**
> Supabase의 `auth.users`는 우리가 컬럼을 추가할 수 없는 "잠긴 표"입니다.
> 그래서 같은 id를 가진 우리 표를 하나 더 만들어 붙입니다. (업계 표준 패턴)

#### ⚠️ 프로필 자동 생성 트리거 (필수)
`auth.users`에 새 유저가 들어오는 순간 **DB가 스스로** `profiles`에 한 줄을 만듭니다.

```sql
-- 0001_init.sql 에 포함
create function public.handle_new_user() returns trigger
language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (id, nickname)
  values (new.id, split_part(new.email, '@', 1));
  return new;
end; $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

> 💡 **왜 필요한가?** 이게 없으면 "`GET /me`를 먼저 불러야 프로필이 생긴다"는 숨은 순서가 생깁니다.
> 프론트가 그 순서를 한 번이라도 어기면(예: 가입 직후 바로 캐릭터 생성) FK 에러가 납니다.
> `GET /me`의 "없으면 생성" 로직은 트리거 이전에 가입한 계정을 위한 **보조 안전장치**로만 남깁니다.

### 2-2. `characters` — 캐릭터 시트

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK→profiles | 주인 |
| `name` | text not null | 캐릭터 이름 (1~20자) |
| `occupation` | text not null | 직업 코드 (02번 문서 6장) |
| `background` | text not null default '' | 유저가 쓴 배경 설정 (최대 500자) |
| `stats` | jsonb not null | **기본 능력치**(보너스 전). `{"strength":2,"agility":3,...}` 합계 15 |
| `deleted_at` | timestamptz NULL | **삭제 표시**. null이면 살아있는 캐릭터 |
| `created_at` | timestamptz | |

⚠️ `hp` / `money` 는 여기 **없습니다.** 캐릭터는 "설계도"이고,
실제 체력은 게임 세션마다 달라지므로 `game_sessions`에 있습니다.
(같은 캐릭터로 여러 판을 할 수 있게 하기 위함)

⚠️ `effective_stats`(직업 보너스 적용값)는 **저장하지 않습니다.** 백엔드가 `stats + occupation`으로 매번 계산합니다.

#### 삭제 = "삭제 표시"(soft delete)
- 삭제 요청이 오면 줄을 지우지 않고 `deleted_at = now()`만 채웁니다.
- 목록/조회/세션 시작에서는 `deleted_at is null`인 것만 씁니다.
- 💡 **왜?** 줄을 진짜 지우면, 그 캐릭터로 했던 **지난 게임 기록(`game_sessions`)이 참조할 대상을 잃습니다.**
  (FK 에러가 나거나, cascade면 게임 기록이 통째로 날아감)

### 2-3. `scenarios` — 시나리오 원본

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `title` | text not null | "을지로 3가의 실종자" |
| `summary` | text not null | 목록에 보여줄 2~3줄 소개 |
| `tags` | text[] not null default '{}' | `{"미스터리","도시"}` |
| `difficulty` | text not null | `easy` / `normal` / `hard` (시나리오 전체 체감 난이도) |
| `estimated_turns` | int not null | 예상 소요 턴 수 (표시용) |
| `max_turns` | int not null default 100 | 이 턴에 도달하면 `ended_timeout` |
| `opening_narration` | text not null | 게임 시작 시 나오는 첫 서술 (AI 호출 없이 고정) |
| `initial_world_state` | jsonb not null | 시작 위치, 시간, 날씨 등 (02번 문서 5장 형식) |
| `initial_inventory` | jsonb not null default '[]' | 시작 소지품 (02번 문서 3장 형식) |
| `gm_guideline` | text not null | AI에게 주는 톤/분위기 지시문 (**유저에게 절대 노출 금지** — 스포일러 포함 가능) |
| `goal_flags` | jsonb not null | 클리어 조건 `{"found_missing_person": true}` |
| `is_public` | boolean not null default false | 목록 노출 여부 |
| `created_at` | timestamptz | |

> 💡 `opening_narration`을 고정 텍스트로 둔 이유:
> 게임 시작 버튼을 눌렀을 때 AI를 기다리면 10초가 걸립니다.
> 첫인상이 "로딩"이면 안 됩니다. 첫 장면은 미리 써둡니다.

### 2-4. `game_sessions` — 게임 한 판

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | |
| `character_id` | uuid FK | |
| `scenario_id` | uuid FK | |
| `status` | text not null | `active` / `processing` / `ended_victory` / `ended_defeat` / `ended_by_user` / `ended_timeout` |
| `locked_at` | timestamptz NULL | `processing`으로 바뀐 시각 (잠금 자동 해제 판단용) |
| `turn_count` | int not null default 0 | 현재까지 **저장된** 턴 수 |
| `resources` | jsonb not null | `{"hp":88,"max_hp":100,"mental":72,"max_mental":100,"money":250000,"inventory":[...]}` |
| `world_state` | jsonb not null | 02번 문서 5장 형식 |
| `summary_so_far` | text not null default '' | 지금까지 줄거리 요약 (AI가 10턴마다 갱신, Step 9) |
| `created_at` / `updated_at` | timestamptz | `updated_at`은 트리거로 자동 갱신 |

#### 상태 묶음 (API 필터에서 씀)
- **진행 중(ongoing)** = `active` + `processing`
- **종료(ended)** = `ended_`로 시작하는 4가지

#### 규칙: 캐릭터 1명은 동시에 1판만
같은 캐릭터로 **진행 중인 세션이 이미 있으면** 새 세션을 만들 수 없습니다. (409 `CHARACTER_IN_USE`)
→ 한 캐릭터가 두 세계에 동시에 존재하는 이상한 상황을 막습니다.

#### ⚠️ `status = 'processing'`의 역할 (턴 잠금)

유저가 전송 버튼을 연타하면 턴이 여러 개 동시에 처리되어 상태가 엉킵니다.

```sql
-- 잠금 획득: "active 이거나, processing인데 5분 넘게 멈춰있는 것"만 잠글 수 있다
update game_sessions
   set status = 'processing', locked_at = now()
 where id = %(session_id)s
   and user_id = %(user_id)s
   and (status = 'active'
        or (status = 'processing' and locked_at < now() - interval '5 minutes'))
returning *;
-- 돌아온 줄이 0개 = 누가 이미 처리 중 → 409 TURN_IN_PROGRESS

-- 잠금 해제: 성공이든 실패든 finally에서 반드시
update game_sessions set status = 'active', locked_at = null
 where id = %(session_id)s and status = 'processing';
```

> 💡 **화장실 문의 "사용중" 표시**와 같습니다. 한 번에 한 명만.
> `locked_at`은 "사용중 표시를 붙인 시각"입니다. 5분이 지나도 안 나오면 고장으로 보고 문을 엽니다.
> (서버가 처리 도중 죽어서 `finally`조차 실행 못 한 경우의 마지막 안전장치)

⚠️ 게임 오버로 끝나는 턴은 해제 시 `active`가 아니라 `ended_*`로 바꿉니다. (05번 문서 노드 6)

### 2-5. `turns` — 턴 기록 (대화 로그)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | **백엔드가 턴 시작 시 미리 만든 uuid** (SSE `turn_started`로 먼저 알려주기 때문) |
| `session_id` | uuid FK | |
| `turn_number` | int not null | 1부터. **UNIQUE(session_id, turn_number)** |
| `client_action_id` | uuid not null | **UNIQUE(session_id, client_action_id)** — 중복 방지 |
| `player_input` | text not null | 유저가 친 행동 |
| `dice_check` | jsonb NULL | 판정 정보(`DiceCheck`, 04번 문서). 판정 없으면 null |
| `narration` | text not null | GM 서술 |
| `state_patch` | jsonb not null default '{}' | 이 턴에 **실제 반영된** 변화 (`StatePatch`, 04번 문서 7-5 ④와 같은 모양) |
| `suggestions` | jsonb not null default '[]' | 추천 행동 (문자열 배열, 0~3개) |
| `token_usage` | jsonb not null default '{}' | `{"input":1200,"output":430}` — 비용 추적용 |
| `latency_ms` | int | 응답 소요 시간 |
| `created_at` | timestamptz | |

> 💡 `token_usage`를 처음부터 기록하는 이유:
> AI API는 쓴 만큼 돈이 나갑니다. 나중에 "왜 이번 달 20만원 나왔지?"를
> 추적하려면 턴별 기록이 있어야 합니다. 나중에 추가하면 과거 데이터가 없습니다.

⚠️ **턴은 "다 끝난 것"만 저장합니다.** AI가 도중에 실패한 턴은 이 표에 없습니다. (04번 문서 7-5 ⑦)

### 2-6. `memories` — 장기 기억 (pgvector, Step 9)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK | |
| `turn_id` | uuid FK | 어느 턴에서 나온 기억인지 |
| `content` | text not null | "주인공은 편의점에서 김수진에게 실종자 사진을 보여줬다" |
| `embedding` | vector(1536) | 의미를 숫자로 바꾼 것 |
| `importance` | int not null | 1~5. 중요한 사건일수록 높게 |
| `created_at` | timestamptz | |

> 💡 **임베딩이 뭔가요?**
> 문장의 "의미"를 1536개의 숫자로 바꾼 좌표입니다.
> 비슷한 의미의 문장은 좌표가 가깝습니다.
> 그래서 "알바생"으로 검색하면 "김수진"이 나온 장면도 찾아집니다.
> **키워드가 아니라 의미로 찾는 검색**입니다.

⚠️ `vector(1536)`은 OpenAI `text-embedding-3-small` 기준 **가정값**입니다. (08번 문서 ②, 아직 미확정)
**임베딩 모델을 바꾸면 차원 수가 달라져서 이 테이블을 다시 만들어야 합니다.**
→ 그래서 `memories` 테이블은 **Step 9 직전에** 모델을 확정한 뒤 별도 마이그레이션(`0004_memories.sql`)으로 만듭니다.
   Step 1에서는 만들지 않습니다. (미리 만들면 나중에 지우고 다시 만들어야 할 수 있음)

## 3. 보안: RLS (Row Level Security)

> 🚨 **이것을 빼먹으면 A유저가 B유저의 캐릭터를 볼 수 있습니다.**
> Supabase에서 가장 흔한 사고입니다.

RLS = "표의 각 줄마다 자물쇠를 다는 것"입니다.

### 우리 프로젝트의 RLS 원칙 (0장과 연결)
1. **모든 테이블에 RLS를 켭니다.** (예외 없음)
2. 정책(policy)은 **"본인 것만 조회(select)"만** 만듭니다. insert/update/delete 정책은 **만들지 않습니다.**
   → 브라우저의 publishable key로는 **아무것도 쓸 수 없습니다.** 쓰기는 오직 백엔드를 통해서만.
3. `scenarios`에는 **정책을 하나도 만들지 않습니다.** (= 브라우저에서 조회 불가)
   → `gm_guideline`(스포일러)이 새어나가지 않게. 시나리오 목록은 백엔드 API가 필요한 칸만 골라서 줍니다.

```sql
alter table profiles      enable row level security;
alter table characters    enable row level security;
alter table scenarios     enable row level security;
alter table game_sessions enable row level security;
alter table turns         enable row level security;

create policy "본인 프로필만 조회" on profiles
  for select using (auth.uid() = id);
create policy "본인 캐릭터만 조회" on characters
  for select using (auth.uid() = user_id);
create policy "본인 세션만 조회" on game_sessions
  for select using (auth.uid() = user_id);
create policy "본인 세션의 턴만 조회" on turns
  for select using (exists (
    select 1 from game_sessions s where s.id = turns.session_id and s.user_id = auth.uid()
  ));
-- scenarios: 정책 없음 (의도적)
```

> 💡 **프론트가 DB를 안 쓰는데 왜 RLS를 켜나?** "이중 잠금"입니다.
> publishable key는 브라우저에 공개되는 키라 누구나 볼 수 있습니다.
> 누군가 그 키로 DB를 직접 두드려도 **남의 데이터는 안 보이고, 아무것도 못 쓰게** 막아두는 것입니다.

- 백엔드는 DB 관리자 계정으로 직접 접속하므로 RLS의 영향을 받지 않습니다.
  → **백엔드 코드가 모든 쿼리에 `user_id` 조건을 직접 넣어야 합니다.** (원칙: 이중 잠금)

## 4. 인덱스 (속도)

```sql
create index on characters (user_id) where deleted_at is null;   -- 내 캐릭터 목록
create index on game_sessions (user_id, updated_at desc);         -- 내 세션 목록
create index on game_sessions (character_id) where status in ('active','processing'); -- 캐릭터 1판 제한 검사
-- turns: UNIQUE(session_id, turn_number)가 곧 "최근 턴 조회" 인덱스 역할을 함
-- memories (Step 9): create index on memories (session_id);
```

> 💡 **pgvector 전용 인덱스(ivfflat/hnsw)는 MVP에서 만들지 않습니다.**
> 기억 검색은 항상 **한 세션 안에서만**(많아야 수백 줄) 하므로, `session_id`로 먼저 좁히고 전부 비교해도 충분히 빠릅니다.
> 특히 `ivfflat`은 **빈 테이블에 만들면 검색 품질이 떨어지는** 특성이 있어서 지금 만들면 오히려 손해입니다.
> 기억이 수십만 줄로 늘면 그때 `hnsw` 인덱스를 추가합니다.

## 5. 마이그레이션 관리 방식

## 6. 백엔드의 DB 접속 방식 (확정)

| 항목 | 결정 |
|---|---|
| 라이브러리 | **psycopg 3 (비동기) + 커넥션 풀** (`psycopg[binary,pool]`) |
| 접속 주소 | Supabase 대시보드 → Connect → **Session pooler** 연결 문자열 (포트 5432) |
| 환경변수 | `DATABASE_URL` (01번 문서 9장) |
| `supabase` 파이썬 라이브러리 | **게임 데이터 읽기/쓰기에 쓰지 않음** |

> 💡 **왜 supabase 라이브러리(REST 방식)가 아니라 직접 연결인가?**
> REST 방식은 "요청 하나 = 작업 하나"라서, **"턴 저장 + 세션 갱신"을 한 묶음(트랜잭션)으로 처리할 수 없습니다.**
> 둘 중 하나만 성공하면 "턴은 저장됐는데 HP는 안 깎인" 반쪽짜리 상태가 됩니다.
> 직접 연결은 "둘 다 성공하거나, 둘 다 없던 일로" 를 보장합니다. (은행 이체: 출금만 되고 입금 안 되면 안 됨)

> ⚠️ **왜 Session pooler 주소인가?**
> Supabase의 "Direct connection" 주소는 IPv6 전용인데, Render 등 배포 서버와 일부 가정용 인터넷은 IPv6가 안 됩니다.
> Session pooler 주소는 IPv4로 접속되므로 로컬·배포 모두 같은 주소를 쓸 수 있습니다.

### 반드시 트랜잭션으로 묶어야 하는 작업
| 작업 | 묶는 내용 |
|---|---|
| 턴 저장 (노드 6) | `turns` INSERT + `game_sessions` UPDATE(자원·세계상태·턴수·상태·잠금해제) (+ Step 9부터 `memories` INSERT) |
| 세션 시작 | 캐릭터 1판 제한 검사 + `game_sessions` INSERT |
