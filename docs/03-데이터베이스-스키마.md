# 03. 데이터베이스 스키마 (Supabase / PostgreSQL)

> 🎯 **DB = 게임의 기록장**.
> 서버가 꺼졌다 켜져도, 브라우저를 닫았다 열어도
> 여기 적힌 것만 살아남습니다.
> 칸 이름과 규칙은 [02번 룰북](02-게임-도메인-규칙.md)의 용어를 그대로 씁니다.

---

## 0. 누가 DB에 접근하나 (⚠️ 먼저 읽기)

| 누가 | 어떻게 | 무엇을 |
|---|---|---|
| **FastAPI 백엔드** | Postgres **직접 연결** (psycopg, 6장) | 모든 게임 테이블 읽기/쓰기 |
| **프론트엔드(브라우저)** | Supabase Auth만 사용 | 로그인/회원가입만. **게임 테이블은 절대 직접 조회하지 않음** |

> 💡 **은행 창구 비유**: 손님(브라우저)은 금고(DB)에 직접 들어가지 않고
> 창구 직원(FastAPI)에게 요청합니다. 창구 직원이 규칙을 확인한 뒤 금고를 엽니다.
> 프론트가 `supabase.from('turns')`로 DB를 직접 읽기 시작하면
> 백엔드의 검증(감정 변화 상한, 턴 잠금 등)을 건너뛰는 뒷문이 생깁니다.

## 1. 테이블 전체 지도

```
auth.users (Supabase가 자동 관리 — 우리가 손대지 않음)
   │   └─ (가입 순간 트리거가 profiles 한 줄 자동 생성)
   │
   └─< profiles          (닉네임 등 추가 정보)
         │
         └─< game_sessions   (이야기 한 편 = 오늘의 설정 + 지금 감정 + 이야기 상태. 완성되면 "여백의 서재"에 보임)
               │
               └─< turns      (프롤로그 / 본문 턴 / 에필로그 기록)
                     │
                     └─< memories  (장기 기억, pgvector, Step 10)
```

`─<` 표시는 "1:N 관계"입니다. (프로필 1개에 이야기 여러 편)

> 💡 **예전 설계에서 사라진 표**: `characters`(능력치 캐릭터), `scenarios`(고정 시나리오), `session_npcs`.
> 이제 주인공은 이야기마다 온보딩에서 새로 정하고(`premise`), 이야기는 AI가 매번 새로 씁니다.
> 온보딩 **예시 칩 목록은 DB가 아니라 백엔드 코드**(`app/game/rules.py`)에 둡니다. (자주 안 바뀌고, git으로 변경 이력이 남음)

## 2. 테이블 상세

> 모든 테이블 공통: `id uuid PK default gen_random_uuid()`, 시각은 `timestamptz`(UTC 저장).

### 2-1. `profiles` — 유저 추가 정보

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | `auth.users.id`와 동일 (FK, `on delete cascade`) |
| `nickname` | text not null | 표시 이름. 기본값 = 이메일의 `@` 앞부분 |
| `created_at` | timestamptz | 가입 시각 |

> 💡 **왜 `auth.users`를 그대로 안 쓰나?**
> Supabase의 `auth.users`는 우리가 컬럼을 추가할 수 없는 "잠긴 표"입니다.
> 그래서 같은 id를 가진 우리 표를 하나 더 만들어 붙입니다. (업계 표준 패턴)

#### ⚠️ 프로필 자동 생성 트리거 (필수)
`auth.users`에 새 유저가 들어오는 순간 **DB가 스스로** `profiles`에 한 줄을 만듭니다.

```sql
-- 0001_init.sql 에 포함
create function public.handle_new_user() returns trigger
language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (id, nickname)
  values (new.id, split_part(new.email, '@', 1));
  return new;
end; $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

> 💡 **왜 필요한가?** 이게 없으면 "`GET /me`를 먼저 불러야 프로필이 생긴다"는 숨은 순서가 생깁니다.
> 프론트가 그 순서를 한 번이라도 어기면(예: 가입 직후 바로 이야기 만들기) FK 에러가 납니다.
> `GET /me`의 "없으면 생성" 로직은 트리거 이전에 가입한 계정을 위한 **보조 안전장치**로만 남깁니다.

### 2-2. `game_sessions` — 이야기 한 편

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK→profiles | 주인 |
| `status` | text not null | `active` / `processing` / `completed` |
| `locked_at` | timestamptz NULL | `processing`으로 바뀐 시각 (잠금 자동 해제 판단용) |
| `premise` | jsonb not null | 오늘의 설정 4요소 (아래 모양) |
| `premise_brief` | text not null default '' | AI 입력 해석기가 정리한 설정 해석 (Step 9부터 채움) |
| `mood` | jsonb not null | **지금 감정** (02번 문서 4장 모양) |
| `story_state` | jsonb not null | **이야기 상태** (02번 문서 5장 모양) |
| `turn_count` | int not null default 0 | 저장된 **action 턴** 수 (프롤로그·에필로그 제외) |
| `summary_so_far` | text not null default '' | 지금까지 줄거리 요약 (Step 10부터 10턴마다 갱신) |
| `title` | text NULL | 이야기 제목. **에필로그 때 채워짐** |
| `deleted_at` | timestamptz NULL | 유저가 지운 이야기 (삭제 표시만) |
| `created_at` / `updated_at` | timestamptz | `updated_at`은 트리거로 자동 갱신 |
| `completed_at` | timestamptz NULL | 에필로그가 저장된 시각 |

#### `premise` 모양
```json
{
  "persona":   { "text": "3년 차 회사원",        "preset_id": "persona_office_3y" },
  "emotion":   { "text": "지독한 권태와 짜증",    "preset_id": null },
  "situation": { "text": "월요일 아침 꽉 막힌 출근길", "preset_id": "situation_monday_commute" },
  "flavor":    { "text": "일상/드라마",          "preset_id": "flavor_daily_drama" },
  "flavor_code": "daily_drama"
}
```
- `preset_id`: 칩으로 골랐으면 칩 id, 직접 입력이면 `null`
- `flavor_code`: 퓨샷 문체를 고르는 열쇠 (02번 문서 3장)
- **한 번 정하면 바뀌지 않습니다.**

#### 상태값
| status | 뜻 | 할 수 있는 것 |
|---|---|---|
| `active` | 진행 중 (다음 입력 대기) | 프롤로그·행동·에필로그 요청 |
| `processing` | AI가 턴을 쓰는 중 (잠금) | 없음 (409) |
| `completed` | 에필로그까지 끝난 **완성작** | 읽기만 |

- 한 유저가 **진행 중인 이야기를 여러 편** 가질 수 있습니다. (책을 여러 권 동시에 읽듯이)

#### ⚠️ 턴 잠금 (`processing`)

유저가 버튼을 연타하면 턴이 여러 개 동시에 처리되어 상태가 엉킵니다.

```sql
-- 잠금 획득: "active 이거나, processing인데 5분 넘게 멈춰있는 것"만 잠글 수 있다
update game_sessions
   set status = 'processing', locked_at = now()
 where id = %(session_id)s
   and user_id = %(user_id)s
   and deleted_at is null
   and (status = 'active'
        or (status = 'processing' and locked_at < now() - interval '5 minutes'))
returning *;
-- 돌아온 줄이 0개 = 누가 이미 처리 중 → 409 TURN_IN_PROGRESS

-- 잠금 해제(실패했을 때): finally에서 반드시
update game_sessions set status = 'active', locked_at = null
 where id = %(session_id)s and status = 'processing';
```
- 성공했을 때는 턴 저장 트랜잭션 안에서 `status`를 `active`(프롤로그·action) 또는 `completed`(에필로그)로 바꾸며 잠금이 풀립니다. (6장)

> 💡 **화장실 문의 "사용중" 표시**와 같습니다. 한 번에 한 명만.
> `locked_at`은 "사용중 표시를 붙인 시각"입니다. 5분이 지나도 안 나오면 고장으로 보고 문을 엽니다.
> (서버가 처리 도중 죽어서 `finally`조차 실행 못 한 경우의 마지막 안전장치)

### 2-3. `turns` — 턴 기록 (이야기의 한 장 한 장)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | **백엔드가 턴 시작 시 미리 만든 uuid** (SSE `turn_started`로 먼저 알려주기 때문) |
| `session_id` | uuid FK | |
| `turn_number` | int not null | 프롤로그 **0**, action **1부터**, 에필로그는 마지막 action 다음 번호. **UNIQUE(session_id, turn_number)** |
| `turn_type` | text not null | `prologue` / `action` / `epilogue` |
| `client_action_id` | uuid not null | **UNIQUE(session_id, client_action_id)** — 중복 요청 방지 |
| `input_kind` | text NULL | `choice` / `free_text` (action 턴만. 나머지는 null) |
| `choice_index` | int NULL | 선택지를 눌렀을 때 그 번호 |
| `player_input` | text NULL | **실제로 반영된 문장** (선택지면 선택지 문구, 직접 입력이면 그 문장). 프롤로그·에필로그는 null |
| `attitude` | text NULL | 이번 입력의 태도 코드 (02번 문서 6장). 선택지면 그 선택지의 태도, 직접 입력이면 기록원 AI가 붙인 값(애매하면 null) |
| `narration` | text not null | AI 서술 |
| `choices` | jsonb not null default '[]' | 이 턴 끝에 준 선택지 2~3개 `[{"text":"...","attitude":"endure"}]` (에필로그는 `[]`) |
| `closure_suggested` | boolean not null default false | "여기서 맺어도 좋을 순간" 신호 |
| `mood_after` | jsonb not null | 이 턴이 끝난 뒤의 `mood` → 모으면 **감정의 파동** |
| `story_state_after` | jsonb not null | 이 턴이 끝난 뒤의 `story_state` (디버깅·복원용) |
| `safety_notice` | boolean not null default false | 위기 신호로 도움 안내를 띄운 턴 (02번 문서 9장) |
| `prompt_version` | text not null | 이 턴을 쓴 프롬프트·퓨샷 버전 (예: `narrator-v1/daily_drama-v1`) |
| `token_usage` | jsonb not null default '{}' | `{"input":1200,"output":430}` — 비용 추적용 |
| `latency_ms` | int | 응답 소요 시간 |
| `created_at` | timestamptz | |

**추가 제약**
```sql
-- 프롤로그와 에필로그는 이야기마다 딱 하나씩만
create unique index turns_one_prologue_epilogue
  on turns (session_id, turn_type)
  where turn_type in ('prologue', 'epilogue');
```

> 💡 `prompt_version`을 처음부터 기록하는 이유:
> 퓨샷 문체 예시는 앞으로 계속 다듬게 됩니다. "이 턴은 어느 버전의 문체 예시로 썼지?"를 알아야
> "예전 버전이 더 좋았네"를 판단할 수 있습니다. 나중에 추가하면 과거 기록이 없습니다.
> (`token_usage`도 같은 이유 — "이번 달 AI 비용이 왜 이렇게 나왔지?")

⚠️ **턴은 "다 끝난 것"만 저장합니다.** AI가 도중에 실패한 턴은 이 표에 없습니다. (04번 문서 5-6 ④)

### 2-4. `memories` — 장기 기억 (pgvector, Step 10)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK | |
| `turn_id` | uuid FK | 어느 턴에서 나온 기억인지 |
| `content` | text not null | "나는 편의점 앞에서 수진에게 처음으로 속마음을 털어놓았다" |
| `embedding` | vector(N) | 의미를 숫자로 바꾼 것 (N은 임베딩 모델에 따라 결정) |
| `importance` | int not null | 1~5. 감정이 크게 움직인 장면일수록 높게 |
| `created_at` | timestamptz | |

> 💡 **임베딩이 뭔가요?** 문장의 "의미"를 수백~수천 개의 숫자로 바꾼 좌표입니다.
> 비슷한 의미의 문장은 좌표가 가깝습니다. **키워드가 아니라 의미로 찾는 검색**입니다.

⚠️ 차원 수(N)가 임베딩 모델에 묶여 있어서, 이 표는 **Step 10 직전에 모델을 확정한 뒤** 별도 마이그레이션으로 만듭니다.

## 3. 보안: RLS (Row Level Security)

> 🚨 **이것을 빼먹으면 A유저가 B유저의 이야기를 볼 수 있습니다.**
> 감정을 털어놓는 게임이라 특히 중요합니다. Supabase에서 가장 흔한 사고이기도 합니다.

RLS = "표의 각 줄마다 자물쇠를 다는 것"입니다.

### 우리 프로젝트의 RLS 원칙 (0장과 연결)
1. **모든 테이블에 RLS를 켭니다.** (예외 없음)
2. 정책(policy)은 **"본인 것만 조회(select)"만** 만듭니다. insert/update/delete 정책은 **만들지 않습니다.**
   → 브라우저의 publishable key로는 **아무것도 쓸 수 없습니다.** 쓰기는 오직 백엔드를 통해서만.

```sql
alter table profiles      enable row level security;
alter table game_sessions enable row level security;
alter table turns         enable row level security;

create policy "본인 프로필만 조회" on profiles
  for select using (auth.uid() = id);
create policy "본인 이야기만 조회" on game_sessions
  for select using (auth.uid() = user_id);
create policy "본인 이야기의 턴만 조회" on turns
  for select using (exists (
    select 1 from game_sessions s where s.id = turns.session_id and s.user_id = auth.uid()
  ));
```

> 💡 **프론트가 DB를 안 쓰는데 왜 RLS를 켜나?** "이중 잠금"입니다.
> publishable key는 브라우저에 공개되는 키라 누구나 볼 수 있습니다.
> 누군가 그 키로 DB를 직접 두드려도 **남의 데이터는 안 보이고, 아무것도 못 쓰게** 막아두는 것입니다.

- 백엔드는 DB 관리자 계정으로 직접 접속하므로 RLS의 영향을 받지 않습니다.
  → **백엔드 코드가 모든 쿼리에 `user_id` 조건(+ `deleted_at is null`)을 직접 넣어야 합니다.** (원칙: 이중 잠금)

## 4. 인덱스 (속도)

```sql
create index on game_sessions (user_id, updated_at desc) where deleted_at is null;  -- 내 책장
-- turns: UNIQUE(session_id, turn_number)가 곧 "최근 턴 조회" 인덱스 역할을 함
-- memories (Step 10): create index on memories (session_id);
```

> 💡 **pgvector 전용 인덱스(ivfflat/hnsw)는 MVP에서 만들지 않습니다.**
> 기억 검색은 항상 **한 이야기 안에서만**(많아야 수십 줄) 하므로, `session_id`로 먼저 좁히고 전부 비교해도 충분히 빠릅니다.

## 5. 마이그레이션 관리 방식

```
supabase/migrations/
  0001_init.sql            ← 테이블 3개(profiles, game_sessions, turns) + 트리거(프로필 자동생성, updated_at)
  0002_rls_policies.sql    ← 보안 정책
  0003_memories.sql        ← (Step 10) vector 확장 + memories
```

- 고정 시나리오가 없어졌으므로 **샘플 데이터(seed) 파일은 없습니다.**
- ⚠️ **파일 이름은 위 목록 그대로** 씁니다. (로드맵·작업지시서도 이 이름을 따릅니다)
- ⚠️ **Supabase 웹 대시보드에서 손으로 테이블을 만들지 않습니다.** 반드시 SQL 파일로 만들어 git에 올립니다.
  (실행은 Supabase SQL Editor에 파일 내용을 붙여넣어 순서대로 실행)
- ⚠️ **이미 실행한 마이그레이션 파일은 고치지 않습니다.** 바꿀 게 생기면 새 번호 파일을 추가합니다.

## 6. 백엔드의 DB 접속 방식 (확정)

| 항목 | 결정 |
|---|---|
| 라이브러리 | **psycopg 3 (비동기) + 커넥션 풀** (`psycopg[binary,pool]`) |
| 접속 주소 | Supabase 대시보드 → Connect → **Session pooler** 연결 문자열 (포트 5432) |
| 환경변수 | `DATABASE_URL` (01번 문서 9장) |
| `supabase` 파이썬 라이브러리 | **게임 데이터 읽기/쓰기에 쓰지 않음** |

> 💡 **왜 supabase 라이브러리(REST 방식)가 아니라 직접 연결인가?**
> REST 방식은 "요청 하나 = 작업 하나"라서, **"턴 저장 + 이야기 상태 갱신"을 한 묶음(트랜잭션)으로 처리할 수 없습니다.**
> 둘 중 하나만 성공하면 "서술은 저장됐는데 감정은 안 바뀐" 반쪽짜리 상태가 됩니다.
> 직접 연결은 "둘 다 성공하거나, 둘 다 없던 일로"를 보장합니다. (은행 이체: 출금만 되고 입금 안 되면 안 됨)

> ⚠️ **왜 Session pooler 주소인가?**
> Supabase의 "Direct connection" 주소는 IPv6 전용인데, Render 등 배포 서버와 일부 가정용 인터넷은 IPv6가 안 됩니다.
> Session pooler 주소는 IPv4로 접속되므로 로컬·배포 모두 같은 주소를 쓸 수 있습니다.

### 반드시 트랜잭션으로 묶어야 하는 작업
| 작업 | 묶는 내용 |
|---|---|
| 턴 저장 (프롤로그·action) | `turns` INSERT + `game_sessions` UPDATE(`mood`, `story_state`, `turn_count`, `status='active'`, `locked_at=null`) (+ Step 10부터 `memories` INSERT) |
| 에필로그 저장 | `turns` INSERT + `game_sessions` UPDATE(`title`, `status='completed'`, `completed_at`, `locked_at=null`) |
